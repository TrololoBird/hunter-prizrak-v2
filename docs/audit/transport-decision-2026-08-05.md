## 1. Что доступно в ccxt 4.5.70 на самом деле

Проверено на установленной версии, `binanceusdm`. Несколько методов, которые обычно называют при обсуждении «исторических данных Binance», **не существуют** — план, построенный на них, обошёлся бы в потерянный день.

| метод | есть в 4.5.70 | замечание |
|---|---|---|
| `fetch_ohlcv` | да | свечи, `since`/`limit`, вес 1 при малых лимитах |
| `fetch_trades` | да | **на `binanceusdm` идёт в `fapiPublicGetAggTrades`** |
| `fapiPublicGetAggTrades` | да | прямой вызов того же эндпоинта |
| `watch_ohlcv`, `watch_trades`, `watch_ohlcv_for_symbols` | да | — |
| `un_watch_ohlcv_for_symbols`, `un_watch_trades_for_symbols` | да | — |
| `create_order_ws` | да | не через `options['ws'] = True` |
| `fetch_open_interest`, `fetch_open_interest_history`, `fetch_funding_rate_history` | да | **запрещены §3**, в системе не применимы |
| `sapiGetFuturesHistDataLink` | да | приватный SAPI, требует ключ — **запрещено §1** |
| `fetch_historical_ohlcv` | **нет** | такого унифицированного метода не существует |
| `fetch_historical_trades` | **нет** | `has['fetchHistoricalTrades']` = None |
| `sapiGetDownloadDataLink` | **нет** | — |
| `fapiPublicGetLongShortRatio` | **нет** | и запрещено §3 |

**Главное из этой таблицы:** `fetch_trades` — это и есть aggTrade. Метод, ради которого держится живой поток, в проекте уже есть и не используется.

Ограничения из исходника ccxt, существенные для пагинации:

* `limit` максимум **1000** записей на запрос;
* `params['fromId']` — пагинация по идентификатору сделки;
* при заданном `since` ccxt сам выставляет `endTime = since + 3600000`, то есть **временное окно ограничено часом**;
* **`fromId` вместе с временным окном даёт ошибку** — ходить надо по `fromId`, иначе платите за нарезку по часам;
* `params['paginate'] = True` включает встроенную пагинацию ccxt.

Вес эндпоинтов по таблице ccxt: `/fapi/v1/aggTrades` — **20**, `/fapi/v1/klines` — **1** (0.4 при малых лимитах), `/fapi/v2/ticker/price` — **~2 без символа, на всю биржу**.

## 2. Замер: чем брать сделки

Считано на реальных данных июля 2026 (4 символа, ТФ 15м/1ч/4ч, кэш суточных архивов, окна структур получены настоящим кодом `levels.structure_window_ms`).

### 2.1. Заменить архив REST-ом целиком — нельзя

| символ | структур | сделок в окнах | запросов | вес | минут бюджета при 2400/мин |
|---|---:|---:|---:|---:|---:|
| BTCUSDT | 103 | 83 874 816 | 83 928 | 1 678 560 | 699 |
| ETHUSDT | 99 | 73 824 202 | 73 868 | 1 477 360 | 616 |
| DOGEUSDT | 81 | 8 110 226 | 8 152 | 163 040 | 68 |
| SOLUSDT | 91 | 16 751 104 | 16 796 | 335 920 | 140 |
| **итого** | **374** | | **182 744** | **3 654 880** | **1 523 ≈ 25 часов** |

Против этого — 124 суточных ZIP. Правило, записанное в archive.py («широкое окно — архив; узкое окно — REST уместен и работает»), верно и теперь измерено: **на широком окне архив дешевле примерно на три порядка.**

Оценка консервативна: окна структур перекрываются, и при дедупликации по суткам цифра падает до ~400 запросов на символ-сутки. Порядок вывода это не меняет.

### 2.2. Суточный прирост REST-ом — дёшево

Ключ в том, что сегодняшние сутки **не перезапрашиваются**: держится курсор `fromId` на символ, и новые сделки дописываются.

| величина | значение | источник |
|---|---|---|
| aggTrades у BTCUSDT за сутки | 399 219 | замер на архиве 2026-08-01 |
| у ETHUSDT | 431 303 | там же |
| у DOGEUSDT | 106 405 | там же |
| у ASTRUSDT | 9 623 | там же |
| запросов на BTC-сутки при `limit=1000` | **400** | 399 219 / 1000 |
| вес | 8 000 | 400 × 20 |
| доля суточного бюджета | **3.3 минуты** | 8 000 / 2400 |
| оценка по всей вселенной (27 символов) | ~6–8 тыс. запросов/сутки ≈ 5/мин ≈ 100 веса/мин | **≈ 4% лимита** |

**Живой поток `aggTrade` этим закрывается полностью.**

⚠ Оценка «6–8 млн сделок в сутки на 27 символов» — экстраполяция с четырёх измеренных символов, а не замер. Проверяется заданием **Ж-3**.

### 2.3. Бары

Каждый ряд опрашивается раз за свой ТФ: 5м 12/ч + 15м 4 + 1ч 1 + 4ч 0.25 + 1Д 0.042 + 1Н 0.006 ≈ **17.3 опроса на символ в час**, × 27 символов = **≈ 467 запросов в час ≈ 0.13/с**. При весе 1–2 это меньше 1% лимита; при пессимистичном 10 — около 3%.

Засев уже сегодня делает 162 REST-запроса за прогон, то есть механика проверена в бою.

### 2.4. «Цена подошла к зоне»

`GET /fapi/v2/ticker/price` **без символа** отдаёт последнюю цену всех инструментов **одним запросом**, вес ~2. Опрос раз в 3 секунды — 20 запросов в минуту, 40 веса, **≈1.7% лимита**. Это дешевле и проще, чем 27 подписок с их снятием при смене списка наблюдения.

### 2.5. Чего вебсокет не может в принципе

Глубина одного REST-запроса — из исходника установленного `ccxt==4.5.70`, файл binance.py чужого пакета, метод `fetch_ohlcv`:

```
# binance docs say that the default limit 500, max 1500 for futures, max 1000 for spot markets
# the reality is that the time range wider than 500 candles won't work right
defaultLimit = 500
maxLimit = 1000
limit = defaultLimit if (limit is None) else min(limit, maxLimit)
```

Биржа разрешает до 1500 баров на запрос, **ccxt режет до 1000**, без явного `limit` просит 500. Что это даёт:

| ТФ | охват 1000 баров одним запросом | месяц истории |
|---|---|---:|
| 1Н | ≈19 лет | 1 запрос |
| 1Д | ≈2.7 года | 1 |
| 4ч | ≈167 суток | 1 |
| 1ч | ≈42 суток | 1 |
| 15м | ≈10.4 суток | 3 |
| 5м | ≈3.5 суток | 9 |

Месяц пятиминуток по всей вселенной (27 символов) — **243 запроса**, меньше минуты бюджета.

⚠ Оговорка из того же исходника: «the reality is that the time range wider than 500 candles won't work right». При ходьбе по `since` страницу разумно держать в пределах 500.

Вебсокет за это время не даёт ничего: он добавляет только бары, закрывшиеся ПОСЛЕ запуска. Чтобы набрать потоком то, что один запрос отдаёт сразу, боту пришлось бы проработать девятнадцать лет на недельном ряде.

⚠ **Поправка 2026-08-05.** В первой редакции здесь стояло «все 199 баров каждого ряда приходят одним REST-запросом при старте». **199 — это число строк в одном сохранённом кадре** (`data/frames/last`), а не размер ответа биржи: кадры других прогонов содержат 500 и 501 строку, и 500 — как раз умолчание ccxt. Глубина ряда задаётся настройкой прогона, а не API. Вывод раздела от поправки усилился, но само число было получено наблюдением не о том, что утверждалось.

Отсюда следствие, которое важнее стоимости: **вебсокет никогда не был источником истории — он был способом приклеивать хвост.** А ряд, склеенный из двух источников (засев REST + хвост WS), — это и есть место, где живёт весь класс Д-3: дубликаты, немонотонность, невидимые разрывы, «пришедшие», но не закрытые свечи. Удаление WS из баров не отнимает данных — оно убирает шов.

## 3. Предлагаемое решение

| потребность | источник | стоимость |
|---|---|---|
| бары всех ТФ | `fetch_ohlcv` по границам ТФ + отступ | ≈467 запросов/час, <1–3% лимита |
| профиль исторических структур | суточный архив, кэш на диске | 124 файла на 4 символа за месяц |
| профиль сегодняшних суток | `fetch_trades` по курсору `fromId` | ≈4% лимита |
| «цена в зоне» | `ticker/price` по всей бирже раз в N секунд | ≈1.7% лимита |
| прокол / пробой / переприор | закрытые тела свечей своего ТФ — то есть бары | входит в строку 1 |

**Суммарно порядка 9% лимита на всё.**

**Следствие: по FOUNDATION у проекта не остаётся ни одного требования, которому нужен вебсокет.** §2.4 и §2.5 решаются закрытыми свечами. §2.2 — профилем на исторических окнах. Вход по §2.7 — лимитка, выставленная заранее, а не по факту касания. Стакан и приватные потоки запрещены §3 и §1.

Теряется одно — **латентность**: 3 секунды против ~0.4 с. Для системы, где оператор торгует руками, а подтверждение занимает от одного бара своего ТФ, это не имеет значения.

### 3.1. Что снимается вместе с WS-слоем

Из реестра `docs/audit/HANDOFF-2026-08-05.md`: **Д-1, Д-2, Д-6, Д-9, Д-10, C-1, C-2, C-8, C-9** и часть **Д-3**.

⚠ **Поправка 2026-08-05, по итогу правки.** В первой редакции здесь стояли ещё **C-6** и **C-5**, и обе позиции названы неверно:

* **C-6 не снимается**: слой удаляется не целиком — `_watch_step` остаётся ради потока сделок и по-прежнему не ловит `OperationFailed` и `UnsubscribeError`.
* **C-5 не снимается, а переезжает**: остаётся один порог тишины, `WS_TRADES_SILENCE_S = 300`. Претензия C-5 была не к таймфрейму как таковому, а к фиксированному числу вместо производного от собственной активности инструмента. Для потока сделок она сохраняется в более острой форме: 300 с молчания у неликвидного символа — норма, у BTC — авария далеко после факта. По §4.1 порог обязан быть относительным (перцентиль собственной истории межсделочных интервалов), а не абсолютным.

Итого удалением подсистемы закрываются **девять** позиций, а не одиннадцать.

### 3.2. Что при этом станет проверяемым

Сейчас счётчик «отдан НЕзакрытый бар» тождественно нулевой: эмиссия и проверка используют одни и те же часы (`is_closed(open_ms, tf, now) == now >= open_ms + tf`, а эмиссия уже потребовала того же условия). На REST появляется **независимый второй источник — ответ биржи**:

```python
got = await ex.fetch_ohlcv(symbol, tf, limit=3)
last_closed = [b for b in got if b[0] + tf_ms(tf) <= clock.now_ms()][-1]
ready = last_closed[0] == expected_last_closed_open_ms(tf, clock.now_ms())
```

`ready` **способен быть False** — значит проверка перестаёт быть тавтологией и начинает измерять. Сколько раз она срабатывает — задание **Ж-1**.

### 3.3. Чего делать нельзя

**Один ряд — один источник.** Если бары идут и REST-ом, и по WS, появляются два ряда, которые надо мирить, и возвращается весь класс Д-3 (дубликаты, немонотонность, невидимые разрывы). Сделки допустимы из трёх источников (архив / REST / поток), но со старшинством и дедупом по `agg_trade_id`.

### Ж-1. Через сколько после границы ТФ биржа отдаёт закрытую свечу

**Зачем:** задаёт константу отступа для опроса баров и превращает мёртвую проверку Д-1 в измеряющую.

**Что делать:** на ~200 подряд границах 1м опрашивать `fetch_ohlcv(symbol, '1m', limit=3)` с отступами 0, 0.5, 1, 2, 3, 5 с и записывать наименьший отступ, при котором последний закрытый бар в ответе равен ожидаемому.

```bash
uv run python - <<'PY'
import asyncio, time
from hunter.exchange import Exchange
from hunter.bars import expected_last_closed_open_ms, tf_ms
from hunter import clock

SYM, TF, N = "BTC/USDT:USDT", "1m", 200
OFFSETS = (0.0, 0.5, 1.0, 2.0, 3.0, 5.0)

async def main() -> None:
    ex = Exchange()
    await ex.open()
    hits = {o: 0 for o in OFFSETS}
    tries = 0
    try:
        for _ in range(N):
            step = tf_ms(TF)
            now = clock.now_ms()
            await asyncio.sleep((step - now % step) / 1000)   # ждём границу
            tries += 1
            for off in OFFSETS:
                await asyncio.sleep(off if off == OFFSETS[0] else 0)
                raw = await ex._ex.fetch_ohlcv(SYM, TF, limit=3)   # noqa: SLF001
                want = expected_last_closed_open_ms(TF, clock.now_ms())
                closed = [r for r in raw if int(r[0]) + step <= clock.now_ms()]
                if closed and int(closed[-1][0]) == want:
                    hits[off] += 1
                    break
    finally:
        await ex.close()
    print(f"границ проверено {tries}")
    for o in OFFSETS:
        print(f"  отступ {o:>4} с: свеча готова в {hits[o]:>4} случаях "
              f"({hits[o]/max(tries,1)*100:.1f}%)")
asyncio.run(main())
PY
```

**Записать:** распределение по отступам; максимальный наблюдённый отступ; сколько раз свеча не была готова и к 5 с.
**Решает:** величину отступа опроса и то, нужна ли повторная попытка.
**Опровержение:** если и при 5 с свеча регулярно не готова, REST-опрос требует другого механизма (например, подтверждения преемником), и аргумент про латентность ослабевает.

### Ж-2. Совпадают ли уже записанные бары с тем, что отдаёт биржа

**Поправка к первой редакции протокола (2026-08-05, замечание владельца).** Здесь стояло «сутки параллельно собирать бары из WS и из REST, чтобы узнать, заменяет ли REST вебсокет», и это была ошибка постановки. История, на которой строятся зоны, приходит **только** засевом REST и архивом (замер 2.5) — вебсокет никогда не был источником, который требуется «заменить». Даже покажи замер расхождение, выбор всё равно пал бы на REST: иначе один ряд собирается из двух источников. Замер, не способный изменить решение, решением не является. Суток живого WS не требуется, и **ничто не обязывает откладывать удаление WS-слоя ради этого задания**.

**Вторая поправка, 2026-08-05, после перехода на REST. Задание закрывается как БЕССИЛЬНОЕ.**
Протокол правки `transport-rest-bars-2026-08-05.md` закрыл Ж-2 с формулировкой «сравнивать не с чем, WS-слой удалён» — это неверно: кадры лежат в `data/frames/` файлами, удаление кода их не трогает, задание исполнимо. Но исполнять его незачем по другой причине: **в сохранённых кадрах хвоста WS практически нет.** Хвост может содержать только бары, закрывшиеся ВО ВРЕМЯ прогона, а все прогоны проекта длились секунды-минуты (боевой — 130 с). Замер кадров: `stage1-stack10` BTC 5м — 501 бар, разрывов 0; `transport` BTC 5м — 500 баров, разрывов 0; оба ряда — окно фиксированного размера, целиком покрытое засевом.

## Приложение A. Скрипт замера стоимости окон структур

Кладётся в `scripts/`, вызывается один раз, результат идёт в протокол. Требует уже наполненного `data/aggcache`.

```python
"""Сколько REST-запросов aggTrades стоят окна структур. Ответ в запросах и в весе."""
import datetime as dt
import math
from decimal import Decimal

import polars as pl

from hunter import archive, levels, swings
from hunter.accumulation import detect as detect_accumulations
from hunter.bars import TIMEFRAME_MS
from hunter.models import NotReady

LIMIT, WEIGHT, RATE = 1000, 20, 2400


def cost(symbol: str, tick: Decimal, series: dict[str, list]) -> tuple[int, int, int]:
    """(структур, запросов, вес). Окна берутся настоящим кодом, число сделок — из кэша."""
    windows = []
    for tf, bars in series.items():
        sw = swings.detect(bars)
        if isinstance(sw, NotReady):
            continue
        for acc in detect_accumulations(bars, sw, tf).closed:
            windows.append(levels.structure_window_ms(acc, bars, TIMEFRAME_MS[tf]))

    days: dict[dt.date, pl.DataFrame | None] = {}
    requests = 0
    for lo, hi in windows:
        d0 = dt.datetime.fromtimestamp(lo / 1000, dt.UTC).date()
        d1 = dt.datetime.fromtimestamp((hi - 1) / 1000, dt.UTC).date()
        trades = 0
        for i in range((d1 - d0).days + 1):
            day = d0 + dt.timedelta(days=i)
            if day not in days:
                path = archive.CACHE_DIR / f"{symbol}-{day.isoformat()}-300000.parquet"
                days[day] = pl.read_parquet(path) if path.exists() else None
            frame = days[day]
            if frame is None:
                continue
            inside = frame.filter((pl.col("bucket") >= lo) & (pl.col("bucket") < hi))
            trades += int(inside["n"].sum())
        # запросов не меньше, чем сделок/1000, и не меньше числа часов:
        # ccxt режет временное окно часом, если идти по since, а не по fromId
        hours = max(1, math.ceil((hi - lo) / 3_600_000))
        requests += max(math.ceil(trades / LIMIT), hours)
    return len(windows), requests, requests * WEIGHT
```
