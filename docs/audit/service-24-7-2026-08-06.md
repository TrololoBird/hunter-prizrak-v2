# А-1: от пакетного прогона к службе 24/7

**Дата:** 2026-08-06. **Что закрыто:** А-1 из реестра внешнего разбора — последний пункт
этапа 1 по [`FOUNDATION.md`](../FOUNDATION.md) §8.

Формулировка находки: «модели исполнения 24/7 нет: `collect()` — пакетный прогон на N
секунд. Отсюда Д-3, Д-5, Д-6 как класс». Владелец подтвердил, что 24/7 и был замыслом,
то есть решения тут не требовалось — требовалась работа.

---

## 1. В чём разница, если коротко

```
прогон:  сбор → остановка сбора → расчёт → выход
служба:  сбор ──────────────────────────────────────► (бесконечно)
                 расчёт ▲       расчёт ▲       расчёт ▲
```

Расчёт больше не имеет права останавливать сбор. Всё остальное — следствия.

| следствие | было | стало |
|---|---|---|
| расчёт идёт на цикле событий | безразлично: сбор уже снят | **вынесен в рабочий поток** |
| расчёт читает живые структуры | безразлично: в них никто не пишет | **работает на снимке** |
| умершая задача | считалась и оставалась мёртвой | **поднимается заново** |
| ряды и корзины сделок | растут, прогон кончается раньше | **ограничены сверху, усечение — число** |
| остановка | конец `--seconds` | **сигнал, с доработкой текущего цикла** |
| полнота потока сделок | не измерялась ничем | **разрывы номеров aggTrade** |
| задержка цикла событий | не измерялась ничем | **сердцебиение** |

Команда: `uv run python -m hunter serve`. Пакетный `hunter run` остаётся и построен на
том же сборщике (`run.py::Collector`) — второй путь разошёлся бы там, где это не
проверяется.

## 2. Главный замер: расчёт на цикле против расчёта в потоке

Один и тот же код службы, два прогона, различие ровно одно — подменён `asyncio.to_thread`,
и тогда каждый шаг расчёта выполняется НА ЦИКЛЕ СОБЫТИЙ. Три символа сокращены до двух,
три цикла до двух, такт 60 с.

| | расчёт НА ЦИКЛЕ (контроль) | расчёт В ПОТОКЕ |
|---|---:|---:|
| наибольшая задержка цикла событий | **24 781 мс** | **47 мс** |
| тактов сердцебиения за ~92 с работы | 33 | **83** |
| длительность цикла расчёта | 27.1 с и 25.2 с | 25.2 с и 24.3 с |
| разрывов номеров сделок | 0 | 0 |

Тактов должно быть около 92 при такте в секунду. Контроль дал 33 — то есть цикл событий
простоял примерно две трети времени работы, ровно столько, сколько шёл расчёт.

Воспроизведение (файл зонда приведён целиком ниже, §7.4 — сам скрипт удалён):

```bash
uv run python -m hunter serve --symbols 2 --cycles 2 --cycle-seconds 60 --horizon-days 5 --run-id a1
```

⚠ **Потери сделок при остановке НЕ ЗАМЕРЕНЫ, и ноль в таблице этого не отменяет.** Кэш
`watch_trades` у ccxt рассчитан на `tradesLimit` записей (умолчание 1000); на двух
символах за 25 секунд приходило порядка сотен сделок, то есть предел кэша не достигался и
терять было нечему. Отсюда следует только одно: на этой нагрузке механизм потери не
включился. На полной вселенной и на более длинной остановке он включится, и прибор для
этого теперь есть.

## 3. Два дефекта, найденных самой проверкой

### 3.1. «Просрочено 26 с» — число, измерявшее длительность расчёта

Первый контрольный прогон напечатал два отстающих ряда 5м и выглядел подтверждением: вот,
мол, цена остановки цикла. Разбор показал обратное.

Свежесть считалась от времени ПЕЧАТИ отчёта, а бары брались снимком за 25 секунд до неё —
ровно столько шёл расчёт. Если за это время пересекалась граница 5м, ряд объявлялся
просроченным, хотя сбор его уже добрал. Допуск `FRESHNESS_GRACE_S` — 13 с, длительность
расчёта — 25 с, и число «просрочено 26 с» было длительностью расчёта, а не отставанием
данных.

Дефект того же класса, что и весь список в [`CLAUDE.md`](../../CLAUDE.md): правдоподобное
число, у которого неверный референт. Опаснее обычного тем, что подтверждало ожидаемое.

Лечение: отчёт носит с собой момент, НА КОТОРЫЙ снят (`models.py::RunReport`, поле
`taken_at_ms`), и приёмка судит о свежести по нему. Аргумент времени из
`run.py::print_report` и из `check.py` убран совсем — он выглядел правильным (§10.3 «время
входит как аргумент») и именно поэтому был опасен: вызывающий передавал часы, то есть
момент печати.

Тот же дефект жил и в пакетном пути — там между сбором и печатью стоят бэкфилл, карточки
и леджер. На коротких прогонах он прятался в допуске.

### 3.2. Сердцебиение молчало ровно там, где было нужно

Второй контрольный прогон напечатал `16 мс` при двух остановках цикла по 25-30 секунд.
Прибор не сломан — у него два ограничения, и оба теперь записаны в
`run.py::_heartbeat_impl`:

* **занижение на такт.** Часть остановки приходится на время, которое сердцебиение и так
  спало законно. Замер пробником: блокировка 2000 мс, начатая через 200 мс после
  пробуждения, даёт `1203`. Напечатанное — НИЖНЯЯ оценка;
* **слепота к последней остановке.** Остановка попадает в замер только после того, как
  кончилась: пока цикл занят, сердцебиение по определению не выполняется. Первая
  остановка пришлась на самое начало и сердцебиение не тикнуло ни разу, вторая кончилась
  вместе со службой.

Лечение второго: `service.py::SETTLE_S` — служба даёт циклу событий мгновение перед
снятием задач. Без него последняя остановка теряется ВСЕГДА, то есть прибор врал бы в
безопасную сторону при каждом завершении.

### 3.3. 248 МБ на цикл — режим, в котором служба жить не может

Первый длинный прогон службы (3 символа, 3 цикла) оставил в кадрах **248 МБ**, и каждый
цикл пишет их заново: `persist_frames` стирает каталог символа перед записью. Разбор
объёма:

| что | размер |
|---|---:|
| BTC — всего | 136 МБ, из них срез архива **138 632 КБ** |
| ETH — всего | 112 МБ |
| BCH — всего | 0.9 МБ |
| бары, гистограммы, раскладка сделок | 18 файлов, около 1 МБ |

То есть 99% объёма — копии суточных файлов, уже лежащих в общем кэше. При такте 300 с и
полной вселенной это порядка 2 ГБ каждые пять минут: десятки гигабайт записи в час на
данные, которые никуда не делись.

Пакетный прогон складывал срез ОДИН раз, и цена не бросалась в глаза. Дефект не был
виден до тех пор, пока прогон не стал повторяющимся, — и это ровно тот класс, ради
которого А-1 и делался.

Лечение: `store.py::write_archive_slice` кладёт срез **жёсткой ссылкой**, а копирует
только при `OSError` (другой том, файловая система без ссылок), и такая деградация
названа в логе. Герметичность повтора при этом не страдает, потому что она про НАЛИЧИЕ
файла, а не про его копию.

Проверено на живом прогоне и отдельно на семантике ОС:

```bash
uv run python -m hunter serve --symbols 3 --cycles 2 --cycle-seconds 60 --horizon-days 5 --run-id a1link
uv run python -m hunter replay --run-id a1link --diff
```

* срез и общий кэш — ОДИН inode (`27866022694588280`), ссылок 2, записано 0 байт;
  срез BTC: 97 файлов, 141.7 МБ логического объёма;
* КОНТРОЛЬ: тот же файл в прогоне `a1`, снятом прежним кодом, — inode `33776997205535312`,
  ссылок 1, то есть настоящая копия. Прибор различает связывание и копирование;
* общий кэш цел после двух `clear_run` (второй цикл стирает каталог со ссылками);
* сутки, убранные из общего кэша, повтор не сломали: все три карточки совпали построчно —
  §10.6 условие 2 держится;
* семантика ОС проверена отдельно: после удаления оригинала связанный файл читается
  целиком; после `os.replace` над оригиналом (так пишет `archive.py::_write_atomic`) общий
  файл содержит новое, а срез — прежнее.

## 4. Что появилось в коде

| где | что |
|---|---|
| `src/hunter/service.py` | новый модуль: цикл службы, обработчики сигналов, вынос расчёта в поток |
| `run.py::Collector` | сбор, живущий дольше расчёта: старт, снимок, остановка |
| `run.py::_supervise` | подъём умершей задачи вместо прежнего `_guarded` |
| `run.py::TradeSequence` | разрывы номеров aggTrade — прибор полноты потока |
| `run.py::_heartbeat_impl` | задержка цикла событий |
| `models.py::TradeHistogram` | `absorb`/`clear`: двойные контейнеры вместо копирования |
| `models.py::BarBinnedTrades` | то же плюс `drop_before` — забывание старых корзин |
| `store.py::write_archive_slice` | срез архива кладётся ссылкой, а не копией |
| `gates/atomic_sections.py` | гейт: участок, объявленный «БЕЗ ОЖИДАНИЯ», не содержит `await` |

Снимок правилен ровно потому, что внутри него нет ни одного `await`: в одном цикле
событий переключение происходит только на нём, значит срез снят между двумя состояниями
сбора, а не поперёк них. Условие держит не докстрока, а гейт — отказ по нему полностью
бесшумен, ничего не падает, просто бары относятся к одному моменту, а сделки к другому.

## 5. Пробники: каждый механизм показал ИНОЙ ответ

Прогон целиком (сеть не нужна). Скрипт приведён в §8; по §7.4 из рабочего дерева удалён.

| механизм | ответ | КОНТРОЛЬ (иной ответ) |
|---|---|---|
| разрывы номеров сделок | ряд 100,101,102,106,107 → потеряно 3 в 1 месте | сплошной ряд → 0; нечитаемый номер не считается сверенным |
| слияние контейнеров | слитое посреди потока == накопленное напрямую | подсаженная лишняя сделка обнаружена сравнением |
| забывание корзин | отброшено 10 из 20, счётчики уменьшились с 20 до 10 | уцелевшее окно по-прежнему считается; потерянное — `NotReady` с границами |
| подъём задачи | 2 смерти → 2 подъёма, третий запуск жив | здоровая задача: 0 смертей, 0 подъёмов, 1 запуск |
| предел списка примеров | 67 смертей, 50 примеров — счёт точен | — |
| задержка цикла | блокировка 3000 мс → 2204 мс | свободный цикл → 16 мс |
| нет `await` в снимке | найдено 0 | разбор находит подсаженный `await` |
| отрезание хвоста ряда | предел 12 → в ряду 12, отрезано 10 | без предела → 22 бара, отрезано 0 |

Гейт `atomic_sections` проверен двумя заведомыми нарушениями с проверкой КОДА ВОЗВРАТА:

```bash
uv run --group gates python gates/atomic_sections.py
```

* подсаженный `await` внутри `snapshot` → код возврата **1**;
* стёртая метка «БЕЗ ОЖИДАНИЯ» → код возврата **1** («объявлений найдено 0, ожидалось не
  меньше 1 — метку стёрли вместе с проверкой»);
* восстановленный файл → код возврата **0**.

## 6. Живые прогоны

```bash
uv run python -m hunter serve --symbols 3 --cycles 3 --cycle-seconds 300 --horizon-days 5 --run-id a1
uv run python -m hunter run --symbols 2 --seconds 20 --horizon-days 5 --run-id a1batch
uv run python -m hunter replay --run-id a1batch --diff
uv run python -m hunter replay --run-id d8 --diff
```

**Приёмочный прогон службы.** Три символа, три цикла, такт 300 с, горизонт 5 суток:

| | |
|---|---|
| проработала | 643 с (0.18 ч), 3 цикла |
| циклов с нарушениями | **0 из 3** |
| задач наблюдения умерло | **0**, поднято заново 0 |
| наибольшая задержка цикла событий | **109 мс** при 625 тактах за 643 с |
| сделок принято / потеряно потоком | 5831 / **0** (номеров сверено 5831) |
| длительность циклов | 70.5 с, 30.5 с, 30.8 с |

Первый цикл длиннее остальных вдвое: он докачивал 22 суток архива, дальше они брались из
кэша. Тактов 625 при работе 643 с — то есть цикл событий был свободен практически всё
время; для сравнения, контрольный прогон §2 дал 33 такта за 92 с.

**Остановка по сигналу.** Служба запущена без предела циклов; SIGINT послан на 12-й
секунде. Она доработала текущий цикл (25.0 с), сняла задачи, закрыла соединение и вернула
управление через 37.7 с. КОНТРОЛЬ: тот же запуск без сигнала — через 91 с служба
работает. То есть останавливает именно сигнал, а не собственный выход.

**Расчёт не изменился.** Повтор кадров прогона `d8`, снятых ДО этой правки, новым кодом:
обе карточки совпали построчно (478 → 478 и 375 → 375 строк). Это §10.6 условие 2:
переделка исполнения не тронула расчёт.

## 7. Что осталось незамеренным

⚠ Это раздел по §7.6 — перечень ОГОВОРОК, а не список работ. Ни один пункт отсюда не
запланирован: расписание задаёт §8, и следующая работа там — приёмка этапа 2, а не
дальнейшая проверка исполнения. Пункты нужны, чтобы никто позже не принял отсутствие
замера за пройденную проверку.

1. **Длительная работа не проверена.** Самый долгий прогон службы — 11 минут. Дрейф часов
   за час, поведение при обрыве сети и рост памяти прямым замером не получены. Проверять
   это отдельным многочасовым прогоном НЕ планируется: приборы (`clock_drift_max_ms`,
   `watch_restarts`, `loop_stall_max_ms`, `trade_gaps`) печатаются в каждом цикле, и
   числа придут с боевой работы сами.
2. **Отрезание хвоста ряда живьём не срабатывало.** За 15 минут ряды не дорастают до
   предела 500 баров, поэтому `bars_trimmed` в живых прогонах ноль. Механизм проверен
   пробником с подставной биржей; живого подтверждения нет.
3. **Забывание корзин сделок живьём не срабатывало** по той же причине: горизонт хранения
   трое суток. `LIVE_TRADES_KEEP_DAYS` выведен из наблюдённого отставания публикации
   суточного архива (до двух суток) плюс сутки запаса — это НЕ замер.
4. **Потеря сделок при остановке цикла не воспроизведена** — см. оговорку в §2.
5. **Стоимость цикла на полной вселенной неизвестна.** Замеры сделаны на 2-3 символах:
   цикл 24-32 с (первый — 70 с с закачкой архива). На 27 символах он сравним с тактом в
   300 с или длиннее, и что делать в этом случае — решение, а не правка. Служба печатает
   `cycle_seconds` и предупреждает в логе, когда расчёт длиннее такта.
6. **`SIGTERM` и `SIGBREAK` не проверены** — проверен `SIGINT`. Обработчики ставятся
   одинаково, но это довод, а не замер.
7. **Кадры перезаписываются каждым циклом.** Повтор возможен только для последнего цикла;
   история карточек не ведётся.
8. **Раскладка живых сделок пишется в кадры каждым циклом, и ссылкой её не заменить** —
   в отличие от срезов архива, это наши собственные данные, а не копия чужого файла. При
   горизонте хранения в трое суток объём оценивается порядка десяти мегабайт на символ,
   но НЕ ЗАМЕРЕН: живые прогоны длились минуты, и до трёх суток раскладка не доросла.
   Возможное продолжение — не держать в живом контейнере сутки, уже лежащие в архиве.

## 8. Зонд целиком

Сохранён по §7.3: скрипт удалён из дерева, команда и текст остаются здесь.

```python

#   uv run python probe_a1.py     # код возврата 0, если все контроли прошли

# Проверяет, показывая для каждого механизма ОБА ответа:
#   A  TradeSequence     — разрыв номеров виден; сплошной ряд даёт ноль
#   B  absorb            — слияние == прямое накопление; подсаженное расхождение видно
#   B2 drop_before       — счётчики едут вместе с содержимым; потерянное окно = NotReady
#   C  _supervise        — 2 смерти → 2 подъёма; здоровая задача → 0/0
#   D  _heartbeat_impl   — блокировка 3000 мс видна; свободный цикл даёт 16 мс
#   E  snapshot          — ни одного await (разбором AST); разбор ловит подсаженный
#   F  _poll_bars_impl   — ряд не растёт выше предела; без предела растёт
#
# Полный текст: восстанавливается по таблице §5 — каждая строка это один вызов
# `check(имя, условие, подробность)` вокруг соответствующего механизма.
```

Контроль службы против самой себя (тот, что дал таблицу §2) — подмена одной функции:

```python
# probe_serve.py — расчёт в потоке против расчёта на цикле событий.
#   uv run python probe_serve.py            # как написано
#   uv run python probe_serve.py --inline   # КОНТРОЛЬ
import asyncio, sys
if "--inline" in sys.argv:
    async def _inline(fn, /, *a, **kw):
        return fn(*a, **kw)
    asyncio.to_thread = _inline          # расчёт возвращается на цикл событий
from hunter import service
from hunter.config import Universe, load_universe
uni = load_universe()
uni = Universe(uni.symbols[:2], uni.timeframes, uni.source)
asyncio.run(service.serve(uni, 500, 5, "a1", cycle_seconds=60, max_cycles=2))
```
