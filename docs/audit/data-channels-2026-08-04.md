# Каналы данных и цена архива: замер вместо утверждений

Дата: 2026-08-04. Повод — вопросы владельца: «почему это 8 гб? ты как построил механизм
запросов данных? rest? websocket? data?»

## Три канала, по коду

| канал | что берёт | где |
|---|---|---|
| **WebSocket** (ccxt.pro) | живые бары `watch_ohlcv`, живые сделки `watch_trades` | `exchange.py::watch_closed_ohlcv`, `watch_agg_trades` |
| **REST** (ccxt) | исторические БАРЫ `fetch_ohlcv` (до 1000 за запрос, с `since`), время сервера | `exchange.py::fetch_closed_ohlcv`, `count_history` |
| **Прямой HTTPS** | суточные ZIP сделок с `data.binance.vision` + `.CHECKSUM` | `archive.py` |

**Сделки по REST не запрашивались вообще** — ни одного вызова `fetch_trades` в дереве.

## Нужен ли архив вообще — вопрос владельца 2026-08-04

> «мне кажется ты почему то переложил rest запросы на запросы data. нужно ли нам вообще
> запросы к data, если rest запросы к api покрывают необходимый набор свечей даже на
> дневном таймфрейме?»

**Для БАРОВ архив не используется нигде, и вопрос снимается проверкой кода.** В
`archive.py` есть единственный путь — `aggTrades/`; klines оттуда качает только зонд
`bar_vs_tick`, и именно затем, чтобы доказать, что барами профиль не построить.
Бары в боевом пути идут исключительно REST-ом (`exchange.py::fetch_closed_ohlcv`).

Замер: **1000 дневных баров — 999 суток за 1.10 с**, 1000 четырёхчасовых — 166 суток за
0.64 с. Владелец прав: REST закрывает бары полностью, включая 1Д.

**Для СДЕЛОК архив нужен, и это тоже замер.** Профиль по стр. 26 натягивается на окно
структуры целиком. Замер на реальном окне (BTC 15м 17.07, 10.8 часа): 8 страниц REST
дали 8000 сделок за 12.5 с и покрыли 311 с рынка из 38 700 — на всё окно нужно
**≈ 994 запроса ≈ 26 минут** против **5.3 с на один ZIP**. Разница ~300 раз на ОДНУ
структуру; структур в горизонте 90 суток 145.

Заменить тиковый профиль барным нельзя — тоже замерено: барный ПОК промахивается мимо
уровня автора на 0.219–0.343% при шуме прибора 0.153%, тиковый — на 0.059%
(`map-depth-2026-08-04.md`).

**Итог: архив — только для сделок и только из-за §5. Бары его не касаются.**

## Опровергнуто: «REST не отдаёт старые сделки»

Докстрока `archive.py` утверждала, что `/fapi/v1/aggTrades` отдаёт сделки «не старше 24
часов». Утверждение взято из документации по памяти и **ни разу не проверялось**.

Замер 2026-08-04, `fetch_trades("BTC/USDT:USDT", since=…)`:

| окно | результат |
|---|---|
| 17.07 06:15 (18 суток назад) | **1000 сделок за 0.45 с**, охват 50.8 с рынка |
| 01.08 00:00 (трое суток назад) | 1000 сделок за 1.69 с, охват 110.1 с |
| 04.08 00:00 (сегодня) | 1000 сделок за 1.41 с, охват 68.5 с |

**REST отдаёт историю.** Ограничение другое — пропускная способность: 1000 сделок
покрывают минуту рынка, значит сутки это ~1440 запросов и ~36 минут против нескольких
секунд на один ZIP.

Правильное разделение: **широкое окно — архив, узкое — REST.** Запрета нет, есть цена.

## Опровергнуто: «нужно 8 ГБ»

Оценка считалась БЕЗ ограничения по возрасту структур и потому включала структуры 1Д
из 2023–2024 годов. Кадр автора охватывает ~40 суток, его уровни лежат в ±8% от цены —
такие структуры его линий породить не могли. Требование считалось для набора, который
не нужен.

Пересчёт с горизонтом (структуры, чьё окно кончается не раньше N суток назад):

| горизонт | ETH: суток / объём / уровней накрыто | BTC: суток / объём / уровней накрыто |
|---|---|---|
| 40 сут | 59 / 354 МБ / 13 из 16 | 40 / 620 МБ / 16 из 20 |
| 60 сут | 59 / 354 МБ / 13 из 16 | 54 / 837 МБ / 16 из 20 |
| **90 сут** | **139 / 834 МБ / 16 из 16** | **54 / 837 МБ / 16 из 20** |
| без границы | 243 / 1458 МБ / 16 из 16 | 355 / 5502 МБ / 20 из 20 |

**1.67 ГБ на оба символа** закрывает весь ETH и 16 из 20 BTC. Последние четыре уровня BTC
(самые глубокие) требуют ещё ~4.7 ГБ — размен плохой, решение владельца.

> ⚠ **ПОПРАВКА 2026-08-04, замер вместо аналогии.** Столбец ETH в таблице выше посчитан по
> **6.0 МБ/сут**, и это число было ПРИНЯТО ПО АНАЛОГИИ с BTC, а не измерено (сказано ниже
> в «непроверенном»). Фактический замер по 137 суткам: **16.31 МБ/сут у ETH против 14.86 у
> BTC** — то есть ETH ТЯЖЕЛЕЕ, а не втрое легче. Все объёмы ETH в таблице занижены в 2.7
> раза; «1.67 ГБ на оба символа» на деле около 3.6 ГБ. Замер: `author-poc-2026-08-04.md`.

## Что осталось непроверенным

- Вес запроса `aggTrades` в лимитах Binance не измерялся; оценка «~1440 запросов на сутки»
  выведена из охвата ответа, а не из документации по лимитам.
- Оценка объёма архива для ETH — 6.0 МБ/сут — принята по аналогии с замеренными 15.5 МБ/сут
  у BTC, а не измерена по файлам ETH.
- Горизонт 90 суток выбран как круглое число вокруг охвата кадра автора (~40 суток), а не
  замерен по тому, откуда реально берутся его уровни. Это станет известно только после
  сверки ПОК на 4ч и 1Д.
- Сутки 2026-08-03 в архиве ещё не опубликованы (HTTP-ошибка у обоих символов).
