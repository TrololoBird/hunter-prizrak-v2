# Обзор транспорта и движка против внешних проектов

**Дата:** 2026-08-17. **Повод:** вопрос владельца «почему закачка такая долгая — изучи
другие проекты, возможно стоит изменить архитектуру или дизайн транспорта и движка;
возможно есть другой способ получения всех необходимых свечей по всем таймфреймам».

Все числа воспроизводимы; команды при каждом. Среда: `evidence/env-2026-08-17.txt`.

---

## 1. Что показал замер НАШЕГО транспорта и движка

**Транспорт.** Пагинация свечей была строго последовательной: ~200 мс на страницу
(время сетевого круга, снято по mtime файлов бэкфилла), при этом бюджет веса биржи
использовался на 4–8% (80–160 из 1800/мин). `OHLCV_PAGE = 499` оптимизировал «бар на
единицу веса» — верный расчёт НЕ ТОЙ величины: узким местом было ожидание, а не вес.
**Починено** тем же днём: страницы вычислимы наперёд и летят параллельно под троттлером
ccxt (`exchange._fetch_ohlcv_paged`, PAGE_CONCURRENCY=8); заодно один таймаут больше не
обрывает хвост окна (в этот день ETH 1m потерял так 619 197 баров из 756 422).

**Движок.** Профиль исполнения повтора (`evidence/profile-replay-2026-08-17.txt`):
76% времени расчёта — `archive.window`: одни и те же сутки сделок перегруппировывались
под каждым перекрывающим окном структуры (329 окон на 3 символа), 8.7 млн строк
конвертировались в Python поштучно, 4 429 обходов каталога глобом (33 с). **Починено:**
кэш суточных гистограмм, накопление колонками в прежнем порядке, индекс частичных
файлов одним обходом. Повтор до/после — **побайтно идентичен** (§10.6):
`/tmp/replay-io-{before,after}.log`, дифф пуст. Гипотеза «затык — GIL в
detect-циклах» замером ОПРОВЕРГНУТА: detect в топ расходов не входит.

## 2. Как транспорт устроен у других — по проектам

| проект | транспорт свечей | что берём как урок |
|---|---|---|
| **jesse** | хранит ТОЛЬКО 1m, старшие ТФ строит сам «on the fly»; позже добавил ОПЦИЮ качать с биржи | главный кандидат: один поток вместо семи; см. §3 — проверено на наших данных |
| **nautilus_trader** | бары агрегирует ЛОКАЛЬНО из потока тиков/котировок (BarAggregator), событийная шина, детерминизм как у нас | свежий хвост можно собирать из уже идущего `watch_trades` без REST вовсе |
| **cryptofeed** | приём отдельно от счёта; в колбэках приёма «не делать ничего вычислительного» | наш снимок+`to_thread` соответствует; болело исполнение горячей точки (§1) |
| **hummingbot** | связь по WS (kline/book стримы), горячие пути на Cython | Cython — новая сборочная зависимость, §10 владельца |
| **OctoBot** | событийные каналы: пересчёт будится ПРИХОДОМ данных, а не циклом по таймеру | идея инкрементального пересчёта вместо полного каждые 300 с |
| **freqtrade** | async ccxt, но пагинация внутри пары тоже последовательная — и в их issue названа медленной | наша боль не уникальна; лечится параллельными страницами (§1) |
| **binance-public-data** (офиц.) | месячные/суточные ZIP klines: один GET вместо тысяч страниц | для ГЛУБОКОЙ истории; ограничено решением владельца 2026-08-11 (§5) |
| **Binance fapi** (док.) | klines limit ≤ 1500; вес: <100→1, <500→2, ≤1000→5, >1000→10 | при упоре в вес 499 оптимален (249.5 бар/вес); при упоре в RTT решает параллельность |
| **ccxt.pro** | `watch_ohlcv` — kline-стримы WS; лимиты Binance USD-M: 1024 стрима/соединение | 27×6=162 стрима влезают в одно соединение — REST-опрос рядов может уйти совсем |

Ссылки: jesse docs (Candles, changelog), nautilus docs (Architecture, Message Bus),

(Async-Channel), freqtrade data-download + issue #1244, developers.binance.com

## 3. ГЛАВНЫЙ ЗАМЕР: старшие ТФ строятся из 1m ТОЧНО — на наших же данных

Вопрос владельца «возможен ли другой способ получения всех свечей» сведён к проверяемому:
совпадают ли бары, собранные из 1m, с нативными барами биржи. На диске есть и то и
другое по 30 рынкам (11.8 млн минуток после сегодняшнего прохода).

**Наивная сборка** (все минуты подряд) расходится на тонких символах: 0.45% корзин 5м
(ASTR 1400, SUPER 975…), у BTC/ETH/SOL — ноль. Механизм найден разбором корзины ASTR
2026-02-18 09:40: **пустая минута (v=0) несёт фантомную цену** — перенесённый close
предыдущей минуты, сделок за которым нет; нативный бар строится по сделкам и фантома
не видит. Свидетель: `evidence/probe-resample-2026-08-17.txt`.

**Правило «минуты с v=0 не участвуют в OHLC» делает совпадение ТОЧНЫМ**:

| ТФ | полных корзин | OHLC расходится | объём (допуск 1e-9 отн.) |
|---|---|---|---|
| 5м | 1 473 924 | **0** | 0 |
| 15м | 491 298 | **0** | 0 |
| 1ч | 122 803 | **0** | 0 |
| 4ч | 30 689 | **0** | 0 |
| 1Д | 7 155 | **0** | 0 |
| 1Н | 1 026 | **0** | 0 |

Свидетель и команда: `evidence/probe-resample2-2026-08-17.txt` (зонд в теле файла).
Итого 2 127 895 корзин, ноль расхождений. Контроль фальсифицируемости: наивная сборка
(без правила) на тех же данных даёт 8 981 расхождение — прибор различает.

⚠ Чего замер НЕ говорит: (а) сравнение только по ПОЛНЫМ корзинам — корзины, где в
хранилище нет части минуток, не сверялись; (б) это исторические бары — поведение живой
границы (незакрытая свеча) отдельный вопрос; (в) точность равна точности самих 1m.

## 4. Варианты архитектуры и их цена

**I. Остаться как есть (уже ускорено).** Параллельные страницы + кэши движка влиты.
Ожидание по расчёту: параллельность даёт предел ~450 тыс. бар/мин по весу против
~100 тыс. последовательно; движок — минус 76%-я горячая точка. Живой замер до/после —
после завершения идущего прохода. Цена: 0. Риск: 0.

**II. jesse-модель: качать и хранить ТОЛЬКО 1m, все ТФ строить локально.**
Транспорт сжимается с 7 рядов на символ до 1. Разовая цена глубины: 1Н требует 200
недель = 3.8 года 1m ≈ 2 млн минуток/символ ≈ 4 010 страниц ≈ 8 020 веса — при
параллельной пагинации ~4.5 мин на символ, разово; дальше — только свежие минутки.
Хранение ≈ 12 МБ/символ. Точность — §3: ноль расхождений на 2.1 млн корзин.
⚠ Это смена ИСТОЧНИКА расчётных рядов — решение владельца (внесено в queue-owner.md).

**III. WS kline-стримы вместо REST-опроса** (`ccxt.pro watch_ohlcv`): 162 стрима в
одном соединении (лимит 1024), REST остаётся только на засев и дыры. Инженерная правка
транспорта; хорошо сочетается и с I, и с II (при II — 27 стримов 1m). Цена: правка
`run._poll_bars` → подписка; замер устойчивости соединения.

**IV. Vision-архивы klines для глубокой истории** (binance-public-data): месячный ZIP
одним GET против тысяч страниц. Затрагивает решение владельца 2026-08-11 «архив удалён
целиком» — то решение мотивировано лагом СВЕЖИХ суток (1-2 дня), который к истории
месячной давности не относится; но пересмотр — только владельцем (queue-owner.md).

**Рекомендация смены:** I уже сделано; II+III — самое сильное сочетание по
простоте и скорости, ждёт владельца; IV даёт выигрыш только при холодном старте.

`evidence/probe-resample-2026-08-17.txt` и `evidence/probe-resample2-2026-08-17.txt`.
⚠ Отпечаток данных: хранилище растёт (боевой проход дописывает свежие бары), повтор
зонда на доросшем кэше даст бОльшие знаменатели — сверять по датам в отпечатке среды.

## 6. Что осталось непроверенным

* живой замер скорости параллельной пагинации (идёт боевой проход — два потребителя
  лимита недопустимы); будет дописан сюда же;
* `watch_ohlcv` живым вызовом не проверялся (только карта возможностей — а она
  объявление, не проверка);
* неполные корзины 1m (дыры хранилища) из сверки §3 исключены;
* поведение живой (незакрытой) границы при локальной сборке ТФ.
