# Бот в группе с многими пользователями: тикер в любом виде, сборка по запросу, канал

**Дата:** 2026-08-17. **Повод:** решение владельца — «бот будет размещён в телеграм-канале
с кучей пользователей, любой пользователь может прислать монету в формате BTC, btc, btcusdt
и в любом другом формате, а бот должен собрать данные и прислать полную аналитику; так же
закреплённые монеты должны отправляться в телеграм-канал».

⚠ **Это протокол замеров и решений, а не свидетельство о работе бота.** Живого запуска с
Telegram по-прежнему не было: у проекта нет ни токена, ни канала. Что именно осталось
непроверенным — последний раздел, и он не «на всякий случай»: там ровно те три вещи,
которые нельзя проверить машиной.

---

## 1. Что изменилось по существу, а не по размеру

| было | стало | почему это не косметика |
|---|---|---|
| тикер искался по 27 символам `config/universe.toml` | по всем рынкам площадки (865 на 2026-08-17) | вселенная — что система СЧИТАЕТ постоянно (§5), а не что ей позволено назвать |
| монеты нет в карте → «не узнаю» | сборка ПО ЗАПРОСУ тем же путём, что `hunter run` | владелец просил «собрать данные», а не «сказать, что данных нет» |
| ответ не говорил, откуда карта | последняя строка сводки называет источник и возраст | карта, посчитанная на лету, и карта, за которой следит служба, стоят разного |
| ответ «не узнаю тикер» на КАЖДОЕ сообщение | в группе молчание — штатный исход | в группе с многими людьми прежнее поведение делало бота генератором мусора |
| транспорт — сырой `ccxt.binanceusdm()` на каждое сообщение | `exchange.Exchange`, открытый один раз | сведённые часы, троттлер веса, отбрасывание незакрытой свечи — всё это уже разобрано там |
| публикации не было | закреплённые (`config/bot.toml`) → канал по закрытию бара 4ч | требование владельца |

**Символ вселенной по запросу НЕ пересобирается никогда.** Не экономия: служба
(`hunter serve`) пишет в те же файлы `data/bars`, и вторая запись из второго процесса по
тому же ряду — потерянные бары без единого исключения.

**Собранное по запросу НЕ идёт в леджер.** Журнал (§10.2) — свидетельство о том, что
система решала сама и постоянно. Сложить туда монету, спрошенную однажды в чате, значит
смешать две выборки в одной статистике; прецедент этого класса уже был —
[`outcome-survey-2026-08-10.md`](outcome-survey-2026-08-10.md).

## 2. Разбор тикера: 19 из 19 при нуле ложных на контроле

Прибор обязан узнавать монету в любой записи. Проверка одним числом («узнал 19») ничего
не стоит: узнавать ВСЁ подряд — тоже способ получить 19. Поэтому рядом идёт контроль —
записи, которые опознаваться НЕ должны.

```bash
uv run python -c "
from hunter.tgbot import MarketIndex
class FakeEx:
    def markets_by_id(self):
        return {'BTC/USDT:USDT':'BTCUSDT','ETH/USDT:USDT':'ETHUSDT','BTC/USDC:USDC':'BTCUSDC',
                'SOL/USDT:USDT':'SOLUSDT','XRP/USDT:USDT':'XRPUSDT',
                '1000RATS/USDT:USDT':'1000RATSUSDT','DOGE/USDT:USDT':'DOGEUSDT'}
idx = MarketIndex.build(FakeEx())
good = ['BTC','btc','btcusdt','BTCUSDT','BTC/USDT:USDT','btc/usdt','\$BTC','#btc','BTC PERP',
        'btc.','  Btc  ','ВТС','биткоин','БИТОК','эфир','ETHUSDT','1000rats','doge','BTCUSD']
ctrl = ['','когда','привет всем','QQQZZZ','/','ETC','...','1234','LUNAUSDT','когда биток вырастет']
miss = sum(idx.resolve(q) is None for q in good)
false = sum(idx.resolve(q) is not None for q in ctrl)
print(f'не опознано нужных: {miss} из {len(good)}; ложно опознано контрольных: {false} из {len(ctrl)}')
"
```

Печатает: `не опознано нужных: 0 из 19; ложно опознано контрольных: 0 из 10`.

Что здесь важно помимо чисел: в контроле стоит `ETC` — настоящий тикер, которого НЕТ в
переданном списке рынков. Он отвергнут, то есть прибор отвечает по списку, а не по
похожести букв. И `LUNAUSDT` — правильная форма записи несуществующего рынка.

⚠ Чего замер НЕ говорит: список рынков здесь поддельный (7 записей). На живой площадке их
865, и совпадений по базе будет больше — правило выбора между ними (`_prefer`)
детерминировано, но замером не проверялось.

## 3. Сборка монеты вне вселенной: путь исполнен целиком

```bash
uv run python -c "
import asyncio
from hunter import clock, log
from hunter.config import load_bot_config, load_universe
from hunter.exchange import Exchange
from hunter.models import NotReady
from hunter.tgbot import MarketIndex, OnDemand
async def main():
    log.configure(); uni = load_universe(); cfg = load_bot_config()
    ex = Exchange(uni.venue); await ex.open()
    try:
        idx = MarketIndex.build(ex); sym = idx.resolve('LTC')
        print('символ:', sym, '| во вселенной:', sym in uni.symbols)
        got = await OnDemand(uni, cfg, horizon_days=2).map_of(sym, clock.now_ms())
        print(got if isinstance(got, NotReady) else f'зон {len(got.zones)} за {got.seconds:.0f} с')
    finally:
        await ex.close()
asyncio.run(main())
"
```

Прогон 2026-08-17, `LTC/USDT:USDT` (вне вселенной), горизонт 2 суток:
**засеяно 2090 баров за 6 запросов; окон структур 12, отброшено по горизонту 35; свечей
профиля дописано 3046; собрано 3 зоны за 11.2 с** (5м — 2, 15м — 1). Повторный запрос
вернулся из памяти тем же объектом.

Три зоны и только младшие ТФ — не дефект, а прямое следствие горизонта в двое суток:
35 структур из 47 отброшены как более старые, а на 4ч и старше двух суток не хватает на
структуру вовсе.

### Цена на БОЕВОМ горизонте: 345 секунд на холодную монету

Та же команда с `horizon_days=180` (`__main__.HORIZON_DAYS`), `LTC/USDT:USDT`,
пустой кэш по этому символу, 2026-08-17:

| что | сколько |
|---|---|
| засеяно баров (6 ТФ) | 75 123 за 6 запросов |
| свечей профиля 1м дописано | 266 100 |
| окон структур | 1685, отброшено по горизонту 11 |
| **времени** | **344.7 с** |
| уровней в карте | 165 (5м — 102, 15м — 44, 1ч — 13, 4ч — 5, 1Д — 1) |

Отсюда два следствия, которые обязан знать владелец:

* обещание бота «это минуты» — не оборот речи: шесть минут на монету, которой ещё не
  было в кэше. Поэтому ожидание НАЗЫВАЕТСЯ отдельным сообщением до начала работы;
* очередь на 8 монет (`build_queue_max`) при худшем раскладе — это около 45 минут
  ожидания у последнего в ней. Число выбрано до замера и замером подтверждено как
  верхняя граница разумного, а не как хорошее время ответа.

### Прогретый кэш почти не помогает: цена — РАСЧЁТ, а не закачка

Тот же символ вторым прогоном, свежий процесс, кэш баров уже на диске: **288.9 с**, из
сети добрано **6 свечей** (вместо 266 100). То есть закачка ушла целиком, а время
сократилось на 16%. **Порядка 84% сборки — это счёт, а не сеть.**

Следствие, которое иначе было бы принято неверно: `map_ttl_minutes` экономит не трафик, а
процессорные минуты, и очередь в 8 монет остаётся сорока минутами независимо от кэша.

### Замирает ли бот на эти минуты: нет, но икает до 4.2 с

Вопрос не праздный: расчёт уходит в рабочий поток (`asyncio.to_thread`), но поток в Python
делит GIL с циклом событий, и «ушёл в поток» не равно «не мешает». Прибор — тот же, что у
службы (`run._heartbeat_impl`): такт 1 с, меряется опоздание собственного пробуждения.

Контроль обязателен: тот же измеритель БЕЗ сборки обязан показать около нуля, иначе он
меряет собственный шум.

```bash
uv run python -c "
import asyncio
from hunter import clock, log
from hunter.config import load_bot_config, load_universe
from hunter.exchange import Exchange
from hunter.tgbot import MarketIndex, OnDemand
TICK = 1.0
class Beat:
    def __init__(self): self.max_ms = 0; self.ticks = 0; self.stop = asyncio.Event()
    async def run(self):
        while not self.stop.is_set():
            t0 = clock.monotonic_ns()
            try: await asyncio.wait_for(self.stop.wait(), timeout=TICK); return
            except TimeoutError: pass
            self.ticks += 1
            self.max_ms = max(self.max_ms, int((clock.monotonic_ns()-t0)/1e6 - TICK*1000))
async def main():
    log.configure(); uni = load_universe(); cfg = load_bot_config()
    ex = Exchange(uni.venue); await ex.open()
    try:
        sym = MarketIndex.build(ex).resolve('LTC')
        idle = Beat(); t = asyncio.create_task(idle.run()); await asyncio.sleep(20)
        idle.stop.set(); await t
        print(f'КОНТРОЛЬ холостых 20 с: тактов {idle.ticks}, опоздание {idle.max_ms} мс')
        beat = Beat(); t = asyncio.create_task(beat.run())
        t0 = clock.monotonic_ns()
        await OnDemand(uni, cfg, horizon_days=180).map_of(sym, clock.now_ms())
        spent = (clock.monotonic_ns()-t0)/1e9
        beat.stop.set(); await t
        print(f'СБОРКА {spent:.0f} с: тактов {beat.ticks}, опоздание {beat.max_ms} мс')
    finally: await ex.close()
asyncio.run(main())
"
```

Прогон 2026-08-17:

```
КОНТРОЛЬ (холостые 20 с): тактов 19, наибольшее опоздание 16 мс
СБОРКА LTC/USDT:USDT: ok, 278 с
ЦИКЛ СОБЫТИЙ: тактов 268 (ожидалось ~278), наибольшее опоздание 4234 мс
```

Читается так: цикл событий ЖИВ всю сборку (268 тактов из ~278 ожидаемых), то есть бот
продолжает отвечать другим людям, — но отдельные паузы доходят до 4.2 с. Против 16 мс
холостого хода это на два порядка больше, значит прибор мерит сборку, а не шум.

⚠ Прибор ЗАНИЖАЕТ: остановка попадает в замер только после того, как кончилась, и часть
её приходится на время, которое такт и так спал законно (разбор — докстрока
`run._heartbeat_impl`). Правильное чтение: остановки были **не короче** 4.2 с.

⚠ Чего замер не говорит: как это выглядит со стороны Telegram. Длинный опрос держит
соединение 10 с, и пауза в 4 с в него укладывается — но это рассуждение, а не замер.

## 4. Темп отправки выведен из лимитов Telegram, а не из вкуса

Источник (прочитано 2026-08-17, core.telegram.org/bots/faq): «In a group, bots are not be
able to send more than 20 messages per minute»; «In a single chat, avoid sending more than
one message per second»; про privacy mode — «Commands explicitly meant for them».

Отсюда, а не из головы, взяты три числа:

* `Pacer.PER_MINUTE = 20` и `Pacer.MIN_INTERVAL_S = 1.0` — прямо из документации;
* `answer_cooldown_s = 60` в `config/bot.toml` — арифметика: ответ бота это 4 сообщения
  (три графика и текст), значит ёмкость группы 5 ответов в минуту, и минута на человека
  означает не больше пятой части ёмкости на одного;
* `TEXT_LIMIT = 4096` — предел `sendMessage` Bot API. Сообщение длиннее не режется, а
  отвергается целиком (`Bad Request: message is too long`).

Проверка темпа (23 сообщения в один чат):

```bash
uv run python -c "
import asyncio, time
from hunter import clock
from hunter.models import ClockSync
from hunter.tgbot import Pacer
clock.set_sync(ClockSync(offset_ms=0, rtt_ms=1, measured_at_local_ms=0, samples=1,
                         server_ms_at_sync=0, measured_at_monotonic_ns=clock.monotonic_ns()))
async def main():
    p, sent = Pacer(), []
    async def call(): sent.append(1)
    t0 = time.monotonic()
    for _ in range(23): await p.send(-100123, 'проба', call)
    print(f'отправлено {len(sent)} за {time.monotonic()-t0:.0f} с, отложено {p.delayed_s:.0f} с')
asyncio.run(main())
"
```

Печатает: `отправлено 23 за 62 с, отложено 62 с` — то есть первые двадцать ушли по одному
в секунду, а двадцать первое дождалось минуты от первого. Без очереди те же 23 сообщения
ушли бы мгновенно, и Telegram потерял бы часть из них.

## 5. Обрезка сводки: прибор способен сработать

Живая карта BTC (69 активных уровней) даёт **3282 знака** при пределе 4096 — то есть
запаса меньше, чем на сотню строк, а число старших уровней в отборе не ограничено ничем.
Контроль — заведомо длинная карта:

```bash
uv run python -c "
from hunter.render import ZoneSpec
from hunter.tgbot import TEXT_LIMIT, compose_text, read_map
live = compose_text('BTC/USDT:USDT', read_map('BTC/USDT:USDT').zones, [], 'Источник: проба.')
huge = tuple(ZoneSpec(side='short', timeframe='4h', price=60000.0+i, zone_lo=59000.0+i,
                      zone_hi=61000.0+i, entry_rule='limit') for i in range(400))
cut = compose_text('BTC/USDT:USDT', huge, [], 'Источник: проба.')
print('живая карта:', len(live), '| 400 зон:', len(cut), '| предел:', TEXT_LIMIT)
print('выброшенное названо:', any('не поместились' in s for s in cut.splitlines()))
"
```

Печатает: `живая карта: 3282 | 400 зон: 4083 | предел: 4096`, `выброшенное названо: True`.

⚠ Число живой карты — замер по РАСТУЩЕМУ источнику. Отпечаток данных на момент замера:
леджер `data/ledger.sqlite3`, BTC/USDT:USDT, активных уровней 69, `last_seen`
1786437872890. Доливка карты изменит и длину.

## 6. Что осталось НЕПРОВЕРЕННЫМ

Три вещи, и ни одна не проверяется без Telegram. Они названы здесь, чтобы не выглядеть
сделанными:

1. **Приём сообщений в группе.** Зависит от выключенного privacy mode у @BotFather —
   настройки на стороне Telegram, которой в репозитории нет. С включённым режимом бот
   увидит только `/coin BTC`, а не `BTC`;
2. **Публикация в канал.** Требует, чтобы бот был администратором канала. Проверяется
   одной командой, когда токен и канал появятся: `uv run python -m hunter bot --publish-now`;
3. **Поведение под настоящей нагрузкой.** Очередь темпа проверена подставным
   отправителем, а не Telegram: `retry_after` в живом чате может приходить и там, где наша
   арифметика считает, что лимит не превышен. Прибор на это уже стоит — счётчики
   `сообщений_потеряно` и `ожиданий_по_лимиту` печатаются при остановке бота.

И одно ограничение, которое проверено и осталось: **во время сборки по запросу в процессе
живут ДВА соединения с биржей** (бот и сборщик), а троттлер веса живёт внутри каждого
экземпляра `Exchange` отдельно. Лимит же Binance считается на IP. Сборка идёт по одной, и
запросов бота между ними единицы, поэтому запас есть — но он не замерен, а рассчитан.
