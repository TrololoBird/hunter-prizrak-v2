# Сводка исходов по измерениям перекоса — и что она нашла в первый же прогон

Дата: 2026-08-10. Повод — правило CLAUDE.md, выведенное из разбора
[`backfill-window-2026-08-04.md`](backfill-window-2026-08-04.md): **у отказов обязана быть
СВОДКА по измерению, вдоль которого возможен перекос.** Тогда сто девяносто честных
отказов подряд читались как «рынок такой», пока их не сложили по таймфрейму.

Для ИСХОДОВ такой сводки не было. Леджер отвечал двумя способами: суммарно по всей базе
(`OWNER_QUERIES['результат в R']`) и разрезом по ТФ без стороны и без типа сигнала. То
есть перекос вида «весь плюс сделан лонгами на 1ч, а ПП стабильно минусовые» не был виден
ничем.

## Что заведено

`store.outcome_survey(conn)` — разрез **тип × ТФ × сторона** с четырьмя знаменателями:
сигналов / закрыто / цель / стоп / неоднозначно, плюс средний R, плюс **возраст клетки в
барах своего ТФ**. Печатается в `hunter check` (§7.5) и отдаёт строку вердикта.

```bash
uv run python -m hunter check
```

Возраст заведён не для полноты, а затем, чтобы пустую клетку **нельзя было объяснить
словами**. Пустая клетка допускает две причины — «сигналы молоды, закрыться не успели» и
«исход не считается вовсе», — и различает их только возраст: ноль исходов при трёх
прожитых барах это данные, ноль при двухстах — дефект.

## Что она нашла в первый же прогон

Сводка на боевом леджере (отпечаток: сигналов 110, исходов 12, уровней карты 575):

| тип | ТФ | сторона | сигналов | закрыто | возраст, баров |
|---|---|---|---|---|---|
| level | 5m | long | 6 | **0** | **1441** |
| level | 5m | short | 8 | 3 | 1566 |
| level | 4h | long | 11 | **0** | 32 |
| level | 4h | short | 19 | **0** | 32 |
| level | 1d | long/short | 8 | 0 | 4–5 |
| pp | все | обе | 8 | 0 | 0 |

Строка `level/5m/long` и есть находка: **шесть сигналов, тысяча четыреста сорок один
прожитый бар, ноль исходов** — при том что шорты того же ТФ закрываются. «Не успели» здесь
не работает: 1441 бар по 5 минут это пять суток.

### Разбор по шагам (а не правдоподобное объяснение)

Причина оказалась не в расчёте исхода, а в том, что **ответ системы выбрасывался**.
`emit.outcome_of` различает пять исходов: `stop`, `target`, `ambiguous`, `not_filled`
(цена не дошла до входа) и `open`. В леджер писались ТОЛЬКО первые три — схема `outcomes`
разрешает ровно их. Остальные два жили одним счётчиком в отчёте прогона и умирали вместе
с процессом.

Следствие: «сигналов 6, исходов 0» означало три разных вещи сразу — цена ни разу не дошла
до входа (законный ответ, стр. 30: вход стоит лимитками), сделка идёт, дефект расчёта. Без
различения сводка кричала бы «дефект» на нормальную работу — то есть учила бы не верить
приёмке, ровно как ложное «битых 0» учит не верить гейту.

## Схема леджера 3 → 4

Заведена `signal_states (signal_id, state, as_of)`, `state IN ('not_filled', 'open')`:

* строка ПЕРЕЗАПИСЫВАЕТСЯ каждым прогоном — это СОСТОЯНИЕ, а не событие; событие
  необратимо и живёт в `outcomes`;
* сделка, ставшая исходом, состояние теряет (`record_signal_state` вычищает записи, на
  которые уже есть исход) — две правды об одной сделке не хранятся;
* миграция перестройки НЕ требуется: переход добавляет пустую таблицу, смысл ни одной
  существующей строки не меняется, и `CREATE TABLE IF NOT EXISTS` её создаёт.

Проверка миграции на КОПИИ боевой базы (не на боевой):

```bash
uv run python -c "import shutil, sqlite3; from pathlib import Path; from hunter import store; src=store.LEDGER_PATH; tmp=Path('data/ledger-migration-test.sqlite3'); shutil.copy(src, tmp); c=sqlite3.connect(tmp); print('версия до', store._schema_version(c)); c.close(); c=store.open_production_ledger(tmp); print('версия после', store._schema_version(c), 'сигналов', c.execute('SELECT COUNT(*) FROM signals').fetchone()[0]); c.close(); tmp.unlink()"
```

Результат: версия 3 → 4, сигналов 110 → 110, исходов 12 → 12, идентификаторы совпали
построчно, состояний на закрытых сделках 0.

## Как сводка читается теперь

Клетки без исходов делятся на три группы, и каждая названа:

* **МОЛОДЫЕ** (≤1 бара своего ТФ) — исход невозможен по построению: `outcome.resolve`
  смотрит только бары ПОСЛЕ `recorded_at`;
* **ОБЪЯСНЁННЫЕ состоянием** — система ответила, просто ответ не «стоп/цель»: столько-то
  мимо входа, столько-то ещё идут;
* **БЕЗ ОБЪЯСНЕНИЯ** — прожили больше бара, состояния нет. Только эти и есть подозрение
  на дефект, и только про них сводка требует разбора.

⚠ Сигналы, записанные ДО появления схемы v4, состояния не имеют и попадают в третью
группу, пока их не пересчитает прогон. Это видно по возрасту и названо здесь, чтобы
первый же вывод сводки не был прочитан как находка дефекта.
