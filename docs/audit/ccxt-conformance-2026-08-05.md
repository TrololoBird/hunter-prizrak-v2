### 1.1. Семь ошибок по версии самой ccxt

Документ ccxt «Seven mistakes crypto exchange API developers make» — прямой чек-лист:

## 2. Что нашлось расхождением с ccxt

### 2.1. ccxt завышает вес `klines` при `limit=500` в 2.5 раза

ccxt объявляет стоимость таблицей `byLimit` (`fapiPublic/get/klines`):
`[[99, 1], [499, 2], [1000, 5], [10000, 10]]`, и `calculate_rate_limiter_cost` берёт
первый разряд, где `limit <= entry[0]`. При `limit=500` условие `500 <= 499` ложно, и
берётся разряд 1000 → **вес 5**.

Замер против заголовка `X-MBX-USED-WEIGHT-1M` (приращение на один запрос):

| `limit` | объявлено ccxt | замерено у биржи | |
|---:|---:|---:|---|
| 3 | 1 | **1** | сходится |
| 99 | 1 | **1** | сходится |
| 499 | 2 | **2** | сходится |
| **500** | **5** | **2** | ⚠ **расхождение в 2.5 раза** |
| 501 | 5 | **5** | сходится |
| 1000 | 5 | **5** | сходится |

Граница разряда у Binance — **500 включительно**, у ccxt — 499. Ошибка ровно на единицу
и ровно в той точке, которая у hunter стоит умолчанием (`--seed-limit 500`).

Последствие не в перерасходе, а в обратном: троттлер ccxt тормозит засев в 2.5 раза
сильнее необходимого. Данные не страдают, страдает время старта.

⚠ Замер сделан на одном символе и одном ТФ; таблица весов у Binance может зависеть от
рынка. Проверено 6 значений `limit`, не весь диапазон.

### 2.2. Троттлер ccxt калиброван вдвое строже лимита биржи

`tokenBucket`: `refillRate = 0.02` за миллисекунду = 20 единиц в секунду = **1200 веса в
минуту**. Биржа в `exchangeInfo` объявляет `REQUEST_WEIGHT/MINUTE/1 = 2400`.

То есть ccxt держит половину разрешённого. Это не дефект — запас осмысленный, — но
означает, что **бюджет из протокола решения (≈9% лимита) надо считать от 1200, а не от
2400**: фактическая доля вдвое выше заявленной, ≈18%. Вывод решения от этого не меняется.

### 2.3. Унифицированный `precision.price` — float, `PRICE_FILTER` — строка

Значения совпадают на всех проверенных символах:

| символ | `PRICE_FILTER.tickSize` | `precision.price` |
|---|---|---|
| BTC/USDT:USDT | `0.10` | `0.1` |
| ETH/USDT:USDT | `0.01` | `0.01` |
| DOGE/USDT:USDT | `0.000010` | `1e-05` |
| ASTR/USDT:USDT | `0.0000010` | `1e-06` |
| 1000RATS/USDT:USDT | `0.0000100` | `1e-05` |

Совпало 5 из 5. **Но `precision.price` — `float`, а `PRICE_FILTER.tickSize` — строка**,
из которой hunter делает `Decimal`. Взять унифицированное поле значило бы вернуть в
основание сетки бинов ровно тот float, из-за которого возникла находка Б-1 (194 из 504
часовых окон с разным ПОК). **Текущий выбор верен и должен быть сохранён при рефакторинге.**

## 3. Дефекты в hunter, найденные этой сверкой

### 3.1. REST-путь не обрабатывал отказы вовсе — ИСПРАВЛЕНО

Главный результат сверки, и он прямо следует из перехода на REST 05.08.

`RateLimitExceeded` и `DDoSProtection` в ccxt наследуют **`NetworkError`**:

```
RateLimitExceeded <- NetworkError <- OperationFailed <- BaseError
DDoSProtection    <- NetworkError <- OperationFailed <- BaseError
```

До правки `fetch_closed_ohlcv` не имел `try` вообще. Следствия:

* в `seed()` — исключение валило **весь прогон**: засев не обёрнут в задачу;
* в `_poll_bars_impl` — `_guarded` пробрасывает, и задача ряда **умирала навсегда**.
  Один сбой на 162 ряда стоил ряда целиком до конца прогона.

Это тем серьёзнее, что после отказа от WS лимит REST — главный отказ системы, а
продолжение после `HTTP 429` даёт бан по IP (`418`) на срок до трёх суток.

Исправлено `_fetch_ohlcv_guarded`: классы разделены, отказ отдаётся как `NotReady`, а не
бросается. Контроль подстановкой исключений:

| подсаженный класс | результат | счётчик «лимит» |
|---|---|---:|
| `RateLimitExceeded` | `NotReady`: лимит биржи | +1 |
| `DDoSProtection` | `NotReady`: лимит биржи | +1 |
| `RequestTimeout` | `NotReady`: сеть | 0 |
| `ExchangeNotAvailable` | `NotReady`: сеть | 0 |
| `BadRequest` | `NotReady`: отказ биржи | 0 |
| `ExchangeError` | `NotReady`: отказ биржи | 0 |
| **без исключения** | **`list`, данные проходят** | 0 |

Последняя строка — обязательный контроль: обёртка, которая «не падает никогда», могла бы
глотать и успешный ответ.

Отдельный контроль на живучесть задачи: ряд, которому биржа отвечает отказом всегда,
**пережил 94 отказа подряд** (`poll_not_ready 94`, задача жива). До правки он умер бы на
первом.

Повтора того же запроса при лимите НЕТ — вместо него пауза `RATE_LIMIT_BACKOFF_S = 60`
(окно веса у Binance минутное). Это прямо следует и из практики: OctoBot комментирует
свой отказ зацикливаться словами «there is a real issue when connecting to the feed.
Don't loop».

### 3.2. Прибор на вес: заголовок читался не тем регистром — ИСПРАВЛЕНО

Разобрано в [`transport-rest-bars-2026-08-05.md`](transport-rest-bars-2026-08-05.md),
раздел 10.3: у синхронного клиента заголовки приходят в `CaseInsensitiveDict`, у
асинхронного — в обычном `dict` со строчными ключами. Механизм проверялся на синхронном,
а применён к асинхронному.

### 3.3. Имена неявных методов ccxt

`fapiPublicGetExchangeInfo` существует; `fapi_public_get_exchangeinfo` — **нет**, хотя
ccxt порождает snake_case-варианты для многих методов (`fapipublic_get_exchangeinfo`
есть). Первая редакция падала `AttributeError` в `open()`. Падение было громким и в
самом начале — это правильное поведение, но имя надо брать из `dir()`, а не по аналогии.

### 3.4. Остаётся открытым: `fetch_time()` без обработки

`fetch_server_ms` вызывается `clock.measure` при открытии и при повторном сведении часов
в конце прогона. Отказ на втором вызове уронит прогон **после** всего сбора данных, но
до сохранения кадров. Не исправлено в этой правке: относится к часам, а не к транспорту
баров, и требует решения, что делать с прогоном, у которого не сошёлся контрольный замер
часов.

### 4.1. Свечи: REST против вебсокета

Из 13 проектов с пригодной выборкой:

* **берут свечи ТОЛЬКО REST-ом — 6** (passivbot, superalgos, bt-ccxt-store, ztom,
  grid_trading_bot, ccxtreplay);
* **используют WS-свечи — 3** (freqtrade, OctoBot, opentrader);
* остальные свечи не берут вовсе (арбитраж по тикерам, экспортёры балансов).

Три потребителя `watch_ohlcv` — **тот же результат, что дала прежняя выборка из пяти**,
хотя рамка отбора здесь другая. Совпадение при смене рамки — единственное, что делает это
число не артефактом поиска. И ни один из троих не полагается на WS как на **единственный**
источник: freqtrade откатывается на REST («Couldn't reuse watch … falling back to REST
api»), OctoBot отдаёт наружу предыдущую свечу по появлению преемника, opentrader
проверяет `has[...]`.

### 4.2. Заголовки лимита не читает практически никто

**1 проект из 13** — OctoBot. Но и там это не контроль, а строка отладочного лога:

```python
f"Last response headers: {self.client.last_response_headers} "
```

плюс сброс `client.last_response_headers = {}`. Управляющего решения по весу не
принимает **ни один проект выборки**.

Отсюда два вывода, и они противоположные:

1. hunter после 05.08 **делает больше типовой практики** — читает лимит из
   `exchangeInfo` и печатает пик потребления долей от него;
2. и именно поэтому **опереться в этом не на кого**. Правило §0.1 «три независимых
   источника» здесь неисполнимо: источников ноль. Прибор построен по документации Binance
   и по здравому смыслу, а не по практике, и это надо помнить.

### 4.3. Чего hunter не делает, а выборка делает

**`exchange.has[...]` перед использованием метода — 6 проектов из 13**, включая всех
троих потребителей WS. У freqtrade это отдельный метод `exchange_has()` с 57
употреблениями и с возможностью переопределения (`exchange_has_overrides`). hunter не
проверял нигде — **закрыто 2026-08-05, разбор в §8.4.**

**Ловят `DDoSProtection`/`RateLimitExceeded` — 4 из 13**: freqtrade (30 употреблений),
OctoBot (6), crypto-exporter, peregrine. У freqtrade это устойчивый образец — `except
ccxt.DDoSProtection` СТОИТ ОТДЕЛЬНО И ВЫШЕ, чем `except ccxt.BaseError`, во всех точках.
hunter после правки 3.1 в этой группе.

### 4.4. Чего в выборке нет ни у кого

Ни один из 16 проектов:

* не сверяет закрытость свечи с **независимым** источником (все — либо по часам, либо по
  преемнику, то есть по одному источнику);
* не читает лимиты из `exchangeInfo.rateLimits`, а не из зашитой константы;
* не хранит `tickSize` как `Decimal` из `PRICE_FILTER` — там, где тик вообще берётся,
  берётся унифицированный float.

Это не повод для самоуспокоения: три пункта, в которых проект расходится с практикой в
свою пользу, — это ещё и три пункта, где ошибку некому заметить.

## 6. Чем эта сверка ограничена

1. **Вес замерен на одном символе и одном ТФ** (BTC/USDT:USDT, 5м), 6 значений `limit`.
   Зависимость веса от рынка не проверялась.
2. **Из каждого проекта бралось до 8 файлов**, отобранных эвристикой по имени пути. Для
   трёх проектов она не сработала, и они исключены из долей; для остальных возможно, что
   нужный код лежит в файле, который эвристика не выбрала. **Нулевое значение в таблице
   означает «в скачанных файлах не найдено», а не «в проекте нет».**
3. **Греп считает употребления, а не поведение.** «freqtrade: 30 упоминаний
   DDoSProtection» говорит о частоте образца, но не доказывает, что он применён везде,
   где нужен.
4. **Выборка смещена в сторону зрелых проектов** — как и прежняя. Отвечает на вопрос «как
   делают аккуратно», а не «как делают вообще».
5. **`RATE_LIMIT_BACKOFF_S = 60` не замерен** — выбран по минутному окну лимита.
   Заголовок `Retry-After` биржа присылает при 429/418, и он не читается.
6. **`HTTP 429` и `418` живьём не наблюдались ни разу.** Ветка разбора проверена только
   подстановкой исключений; что именно шлёт Binance и в каком классе ccxt это приходит на
   практике — не подтверждено.
7. **Практика по чтению заголовков лимита отсутствует** (0 из 13 в управляющей роли),
   поэтому §0.1 по этому решению не выполняется и выполнен быть не может.

## 7. Дополнение 2026-08-05: сигнальный жанр и то, чего мы НЕ используем

Замечание владельца: выборка была из торговых ботов, а сам репозиторий **crypto-signal**
не изучен; и сверялось только то, что проект уже зовёт, — такая сверка по построению не
способна найти пропущенное. Оба возражения справедливы.

### 7.1. Пять проектов сигнального жанра

| проект | звёзд | свечи | лимит | повтор | `active` |
|---|---:|---|---|---|---|
| CryptoSignal/crypto-signal | 5612 | REST | `sleep(rateLimit/1000)` вручную **сверх** троттлера | tenacity, 3 попытки на `NetworkError` | нет |
| jesse-ai/jesse | 8293 | REST | — | — | нет |
| Haehnchen/crypto-trading-bot | 3510 | REST | — | — | нет |
| CyberPunkMetalHead/Binance-volatility-trading-bot | 3491 | REST | — | — | нет |
| nguyennoapp/tuntunbot | — | REST | — | есть | нет |
| OfficialGIGA/crypto-signal-scanner | — | REST | 1 упоминание | — | нет |

**Свечи вебсокетом не берёт НИ ОДИН из сигнальных проектов.** Жанр отличается от
исполняющих ботов: сигнальная система сканирует много рынков редко, и подписка на каждый
не окупается. Это независимо подтверждает решение по транспорту — уже третьей рамкой
отбора.

**Дефект в самом звёздном из них.** crypto-signal:

    @retry(retry=retry_if_exception_type(ccxt.NetworkError), stop=stop_after_attempt(3))
    def get_historical_data(...):
        historical_data = self.exchanges[exchange].fetch_ohlcv(...)
        time.sleep(self.exchanges[exchange].rateLimit / 1000)

`RateLimitExceeded` наследует `NetworkError` (`isinstance` — True), а `tenacity`
отбирает исключения именно по `isinstance`. Значит **ответ «лимит превышен» повторяется
три раза подряд** — ровно то, за что Binance банит по IP. Это тот же дефект, который был
у hunter до правки 3.1, в проекте с 5612 звёздами.

Оговорка: код читан, не исполнен. Утверждение о поведении `tenacity` выведено из
семантики `retry_if_exception_type` и проверенной иерархии ccxt, а не из прогона.

### 7.2. НАЙДЕНО ТИХИМ: делистнутый символ выглядит здоровым рядом

Главный результат дополнения, и найден он именно взглядом на неиспользуемое.

`market["active"]` hunter не читал нигде. На бирже **124 неактивных рынка из 852**.
Замер по 50 барам 5м:

| символ | `active` | баров | разных `close` | сумма объёма |
|---|---:|---:|---:|---:|
| BTC/USDT:USDT | True | 50 | **48** | 15964.12 |
| OMG/USDT:USDT | False | 50 | **1** | **0.00** |
| WAVES/USDT:USDT | False | 50 | 1 | 0.00 |
| MKR/USDT:USDT | False | 50 | 1 | 0.00 |
| DEFI/USDT:USDT | False | 50 | 1 | 0.00 |

Снятый с торгов символ **не даёт отказа**. Биржа продолжает отдавать бары с ТЕКУЩИМИ
метками времени; ряд заморожен — одна цена, нулевой объём.

Почему это опаснее отказа: **все проверки приёмки напечатали бы зелёное.**
Свежесть сходится (метки текущие), разрывов нет, бар не битый — `o=h=l=c` проходит
определение свечи. Система строила бы уровни и эмитировала сигналы по инструменту,
которым нельзя торговать, и ни одна строка отчёта не возразила бы.

**Исправлено:** `instrument()` возвращает `NotReady("снят с торгов (active=False)")`.
Контроль — прибор способен на оба ответа:

| символ | `active` | результат |
|---|---:|---|
| BTC/USDT:USDT | True | `Instrument tick=0.10` |
| OMG/USDT:USDT | False | `NotReady`: снят с торгов |
| NOSUCH/USDT:USDT | — | `NotReady`: нет на бирже |

⚠ **Дефект ЛАТЕНТНЫЙ.** Во вселенной проекта на 2026-08-05 неактивных символов нет — 0
из 27. То есть он ждёт первого делистинга среди наших 27, а вселенная закреплена и
автоматически не пересчитывается (§5). Ждал бы молча.

**Ни один из 21 проекта обеих выборок `active` не проверяет.** Опереться снова не на кого.

### 7.3. Что ещё доступно и не используется

Из 42 публичных возможностей `binanceusdm` (приватные и запрещённые §3 отброшены) hunter
зовёт 8. Разобрано по существу, а не списком:

| возможность | что даёт | нужна ли |
|---|---|---|
| `fetchLastPrices` | цены **728 символов одним запросом, вес 2** | **да** — это и есть сторож «цена в зоне» из §2.4 протокола решения, уже готовым унифицированным методом. Протокол предлагал звать сырой эндпоинт |
| `fetchStatus` | `{'status': 'ok'}` либо обслуживание | **да, дёшево** — сейчас регламентные работы биржи неотличимы от сетевого сбоя |
| `watchTradesForSymbols` | ОДНА подписка вместо 27 | да, при возврате к 24/7 — прямой аналог C-2 для сделок |
| `unWatchTrades` и `unWatchTradesForSymbols` | отписка | да, при смене вселенной на ходу; сейчас подписки живут до конца прогона |
| `load_markets(reload=True)` | перечитать рынки | **да, для 24/7**: тик и `active` читаются ОДИН раз при старте и дальше живут в `_instruments` навсегда |
| `params['paginate']` и четыре стратегии | встроенная пагинация | нет: `count_history` ходит по `since` сам и это проверено |
| `fetchOHLCVWs` | свечи запросом ПО ВЕБСОКЕТУ | нет: семантически тот же запрос, но добавляет соединение |
| `fetchMarkOHLCV`, `fetchIndexOHLCV`, `fetchPremiumIndexOHLCV` | свечи маркировочной и индексной цены | нет: курс работает по обычным свечам |
| `fetchADLRank`, `fetchTradingFee`, `fetchTradingFees` | — | нет |

**`load_markets(reload=True)` — самое существенное из неиспользуемого.** Кэш
`self._instruments` не сбрасывается никогда. Для пакетного прогона на минуты это
безразлично; для сервиса 24/7 (§8, вопрос А-1) означает, что ни смена `tickSize`, ни
делистинг посреди работы замечены не будут — включая проверку `active`, добавленную выше.
Правка бессмысленна до решения владельца по А-1 и потому здесь только названа.

### 7.5. Чем дополнение ограничено

1. **Файлы сигнальных проектов брались точечно** — у crypto-trading-bot и tuntunbot

3. **Заморозка ряда замерена на четырёх делистнутых символах** и на одном ТФ. Что

4. **`active` проверяется только в `instrument()`.** Если рынок снимут во время работы
   процесса, кэш `_instruments` и `markets` этого не заметят — см. 7.3.
5. **`fetchStatus` не подключён**, только замерен: `{'status': 'ok'}` на исправной бирже.

### 8.2. Где совпадаем с практикой

**Свечи запросом, а не подпиской.** Девять из десяти сигнальных проектов и шесть из
тринадцати торговых берут свечи REST-ом. Решение от 05.08 совпадает с преобладающим
образцом, причём в сигнальном жанре — почти единогласным. Это третья независимая рамка
отбора, дающая тот же ответ.

**Встроенный троттлер включён.** Как у всех, кто вообще настраивает клиента.

### 8.3. Где расходимся сознательно

**Ручная пауза сверх троттлера — 6 из 10 сигнальных, у нас нет.**
Формы у них разные: дублирование `sleep(rateLimit/1000)`, прибавка 4000 мс именно для
Binance, фиксированные паузы между проходами. Общее у всех одно: **никто не измеряет
фактическое потребление** — пауза подбирается вслепую.

У нас вместо паузы прибор: `X-MBX-USED-WEIGHT-1M` читается после каждого запроса, пик
печатается долей от лимита, прочитанного у самой биржи. Это не «лучше по определению» —
это другой размен: они платят временем за спокойствие без замера, мы платим сложностью
за замер. Но замер даёт то, чего пауза не даёт никогда: **число, по которому видно, нужна
ли пауза вообще.** Наш замер — 2.0% и 7.0% лимита на прогонах 3 символов; прибавка
4 секунд к каждому запросу при таком потреблении была бы платой ни за что.

**Определение закрытости свечи.** Из 23 проектов ни один не сравнивает ответ биржи с
собственными часами. Десять сигнальных не определяют закрытость вообще; двое торговых
используют правило преемника. Мы делаем третьим способом, и причина не в качестве, а в
задаче: нам нужен не только признак «можно брать», но и **замер опоздания биржи**
(`poll_late`). Преемник этого не даёт — он либо есть, либо нет.

**`market["active"]`, лимиты у биржи, заголовки потребления, тик как `Decimal`** — по
каждому пункту мы одни из 26. Это надо держать в голове как риск, а не как достижение:
**§0.1 требует трёх независимых источников, а здесь их ноль.** Опереться не на кого, и
ошибку заметить некому. Основание — только документация биржи и цена отказа.

### 8.4. Где отставали — `exchange.has[...]`, ЗАКРЫТО 2026-08-05

Это был **единственный пункт, где нас обходила практика**: проверяют 6 из 13 торговых
ботов, включая всех троих потребителей вебсокета; у freqtrade это отдельный метод с 57
употреблениями. Мы не проверяли нигде.

⚠ В сигнальном жанре `has[...]` не проверяет никто (0 из 10), так что «практика» здесь —
свойство более зрелых торговых ботов, а не жанра.

**Что сделано.** `REQUIRED_CAPABILITIES` — три возможности, каждая с причиной, почему без
неё прогон бессмыслен:

| возможность | зачем |
|---|---|
| `fetchOHLCV` | бары всех ТФ — без них нет ни структур, ни уровней (§2.4, §2.8) |
| `fetchTime` | сведение часов с биржей — §6 запрещает судить о закрытости по локальным |
| `watchTrades` | поток сделок для профиля объёма (§2.2, §5: aggTrade) |

Проверка стоит в `open()` **после `load_markets`** (часть `has` уточняется ответом биржи)
и **до всего остального**: отказ обязан случиться в начале прогона, а не из середины
стека спустя минуты сбора. При нехватке — `CapabilityMissing` с поимённым списком.

**Почему это не косметика.** Цена отсутствия проверки — не отказ биржи, а ФОРМА отказа.
Снятый или переименованный метод даёт `AttributeError` из середины стека без указания на
причину. Ровно это случилось в этой же сессии с `fapi_public_get_exchangeinfo`, которого
в ccxt нет: падение было громким, но объясняло себя плохо. Теперь такой отказ выглядит
так:

```
binanceusdm: нет необходимых возможностей ccxt — fetchOHLCV (бары всех ТФ — без них
нет ни структур, ни уровней (§2.4, §2.8))
```

**`'emulated'` — отдельный случай.** `has` принимает `True`, `False`, `None` и
`'emulated'`; последнее означает, что ccxt собирает метод из других. Отсутствием это НЕ
считается, но печатается как деградация: метод работает, а стоить и вести себя может
иначе.

**Контроль — проверка способна дать иной ответ:**

| подстановка | отсутствует |
|---|---:|
| всё на месте | **0** |
| `has["fetchOHLCV"] = False` | 1, назван поимённо |
| `has["watchTrades"] = False` | 1 |
| `has["fetchTime"] = False` | 1 |
| `has["fetchOHLCV"] = "emulated"` | **0** + строка деградации |

Сквозной контроль: с подменённым `describe()` без `fetchOHLCV` метод `open()` бросает
`CapabilityMissing`; на исправной бирже тот же `open()` проходит и сводит часы. То есть
отказ обусловлен биржей, а не кодом.

В приёмке печатается знаменатель — `возможности ccxt проверены до прогона: 3,
отсутствует 0 — иначе прогона бы не было`.

⚠ Ограничение: проверка охватывает **три** метода из восьми, которые проект зовёт у ccxt.
Остальные пять (`load_markets`, `close`, `markets`, `last_response_headers`,
`fapiPublicGetExchangeInfo`) в `has` не представлены: это либо атрибуты, либо неявный API
биржи. Для них `has` не поможет, и `fapiPublicGetExchangeInfo` по-прежнему способен
исчезнуть при обновлении ccxt незамеченным.

### 8.6. Чего мы не берём и почему

Разбор неиспользуемых возможностей ccxt — в §7.3 настоящего документа. Короткая сводка
относительно выборок:

* **`watchOHLCVForSymbols`** — применяет 1 проект из 26 (Haehnchen). Нам не нужен: свечи

* **`watchTradesForSymbols`** — не применяет никто; нам был бы полезен (одна подписка

* **ручная пауза сверх троттлера** — применяют 7 из 26; сознательно не берём, см. 8.3;
* **голый `except Exception`** — применяют 7 из 10 сигнальных; не берём: он делает отказ
  сети неотличимым от отсутствия данных, что запрещено §4.3;
* **`params['paginate']`, `fetchOHLCVWs`, свечи маркировочной цены** — не применяет никто
  из 26, и нам не нужны.
