## 1. Число строк (Rows Layout / Row Size)

**Два режима.** Вход `Rows Layout` ∈ {`Number of Rows`, `Ticks Per Row`}; вход `Row Size` —
число, чей смысл зависит от режима (S2, S3):

* `Number of Rows`: `Row Size` — ЦЕЛЕВОЕ число строк гистограммы; тики на строку считаются
  автоматически: **`Ticks Per Row = (Histogram Top − Histogram Bottom) / Number of Rows / Tick size`** (S2, S3);
* `Ticks Per Row`: `Row Size` — число тиков в каждой строке напрямую (пример из S3: 25 → каждая строка высотой 25 тиков).

**Округление (важно для побитового совпадения).** Если формула даёт нецелое, TV округляет
Ticks Per Row вверх ИЛИ вниз — выбирается то направление, при котором итоговое число строк
БЛИЖЕ к значению `Row Size`; итоговое число строк при этом МОЖЕТ ПРЕВЫСИТЬ заданное —
добавляются строки, чтобы покрыть весь диапазон данных (S2, S3: "It may also create
additional rows to ensure all of the data is represented"). То есть заданные "24 строки"
на конкретном диапазоне могут дать фактически иное число строк.

**Умолчание "24 строки" ОФИЦИАЛЬНО НЕ ПОДТВЕРЖДЕНО.** Ни одна страница справки TV (S2, S3, S4)
значение по умолчанию не называет. Свидетельства расходятся:
* Trader Dale (S8), показывая живые настройки TV: "By default, it is about 100" (сам рекомендует 1000);
* LuxAlgo (S11): "commonly 24 to 100 (platform dependent)" — 24 упоминается как типичное, но не как умолчание TV;
* MarcosACH (S10) в своей реализации ставит default 100.
Проверяется только живым открытием инструмента (см. "Что выяснить не удалось", п. 1).

## 2. Раскладка объёма бара по строкам (intrabar-механика)

**Общий принцип (S1, официально):** профиль строится не по барам текущего ТФ, а по барам
МЛАДШЕГО ТФ внутри диапазона: "to calculate the volume profile for one daily session, the
system loads all 1-minute bars that were traded in that daily session, analyzes the price
levels where they were traded and the direction of price movement".

**Правило выбора младшего ТФ (S2 — прямо для Fixed Range VP; то же в S4 для VRVP):**
последовательность **1, 5, 15, 30, 60, 240 минут, 1D**; берётся первый ТФ из
последовательности, при котором число баров в диапазоне расчёта **меньше 5000**.
Дополнения (S2): если весь диапазон ≤ 5 минут или график секундный — берутся 1-секундные
данные независимо от числа баров; на фьючерсах и спредах — не порог 5000, а ТФ на одну
ступень ниже текущего. Число доступных младших баров ограничено тарифом × depth ratio (S2).
(У Volume Footprint иерархия иная — 1 tick → 1s → 1m → 60m по доступности данных, S5 —
что подтверждает слова S1: правило выбора intrabar-ТФ у каждого инструмента своё.)

**Как объём ОДНОГО intrabar-бара делится по строкам — официальная справка НЕ говорит.**
S1 проверен дословно: формулы нет, только "analyzes the price levels where they were traded".
Косвенные свидетельства сообщества (все НЕофициальные):
* alphachart_tv (S12): "Distributes each bar's volume proportionally across the price rows it spans" — пропорционально перекрытию диапазона high-low бара со строкой;
* LuxAlgo (S11): "For each bar b in the range, distribute its volume V_b across the rows that the bar's high-low span overlaps (evenly by default)", и честная оговорка: "Step 3 varies by platform: even split across the bar's span, all volume placed at one price such as the close, or exact allocation from tick data";
* mervinj3546 (S9) про intrabar-режим: младшие бары нужны, "so volume is placed where it actually traded instead of spread evenly across each bar's range" — без младших данных Pine-скрипты мажут объём равномерно по диапазону бара; с ними — та же раскладка, но по узким диапазонам минутных баров.

**Рабочая модель для порта:** объём каждого младшего бара размазывается РАВНОМЕРНО по
строкам, пересекающимся с его [low, high], пропорционально доле перекрытия. При минутных
барах и десятках строк узкий бар почти всегда целиком в 1–2 строках, так что расхождение
моделей мало́. Побитовое равенство с TV этим НЕ гарантируется (см. п. 7).

**При отсутствии младших данных:** официального правила для FRVP нет. Pine-скрипты (S9)
при исчерпании лимита "falls back to the standard method" — раскладка по барам текущего ТФ.
Для нашего порта вопрос снят: данные свои.

## 3. Up/Down volume (и это НЕ buy/sell)

* TV прямо пишет (S1): используется "up/down volume instead of buy/sell volume … based on
  a price direction inside bars". Никакого определения агрессора — только направление
  intrabar-бара; ВЕСЬ объём бара падает в одну категорию.
* Правило (S1, общая справка): **close ≥ open → Up; close < open → Down.**
* ⚠ Страница инструмента рисования (S3) формулирует границу ИНАЧЕ: "if close > open …
  up volume, if close <= open, it's down volume" — равенство close=open отнесено к Down.
  Противоречие двух официальных страниц; на POC/VA не влияет (Total не зависит от
  разбиения), влияет только на отображение Up/Down и Delta.
* Footprint (S5) для close=open добавляет третье правило: сравнение с close предыдущего
  бара — но документировано только для футпринта.
* В Fixed Range разбиение ЕСТЬ: вход `Volume` ∈ {`Total`, `Up/Down`, `Delta`} (S2, S3).
  Умолчание инструмента рисования — Up/Down, два цвета (S8: "The default setting is the
  Up/Down Volume scheme"; S6: "Yellow and blue rows = down volume and up volume").

## 4. POC

* Определение (S1): "The price level for the time period with the highest traded volume" —
  строка с максимальным СУММАРНЫМ (up+down) объёмом; рисуется красной линией (S6).
* **Ничья по максимуму между строками:** официально НЕ документирована. Документирована
  только ничья КАНДИДАТОВ Value Area (п. 5). Замер репозитория
  (docs/audit/04-poc-tv-emulation.md) показал: при 24–200 строках ничьи максимума
  реальны (227 случаев на выборке), значит тай-брейк придётся выбрать нам и пометить как
  соглашение. Естественная экстраполяция правила VA-ничьей: нижняя/верхняя по явному
  правилу — но это НАША экстраполяция, не TV.
* **Цена строки:** официальная справка НЕ говорит, какая цена приписывается строке
  (низ/центр/верх). Замер репозитория показал, что выбор значим при малом числе строк —
  фиксировать в порте как явное соглашение (линия POC на графике TV визуально идёт по
  середине строки; официального подтверждения нет).

## 5. Value Area 70% — точный алгоритм TV (S1, дословные шаги)

1. Total volume профиля × процент (умолчание 70%) → целевой объём VA.
2. Старт с POC: включить его строку, вычесть её объём из цели.
3. Взять СЛЕДУЮЩУЮ ОДНУ строку над включённой областью и следующую одну под ней.
4. Сравнить их объёмы, выбрать БОЛЬШУЮ.
5. Попытаться добавить выбранную строку:
   * "If adding it does not exceed the remaining target volume, include it and update the
     corresponding boundary (VAH if added above, VAL if added below)."
   * "If it would exceed the target, stop — the value area is complete." — TV
     ОСТАНАВЛИВАЕТСЯ ПЕРЕД превышением цели, а не добавляет перевалившую строку.
6. Дальше: следующая строка с той стороны, куда только что добавили, против ТЕКУЩЕЙ
   (той же) строки с противоположной; повторять шаги 4–6.
7. Ничья кандидатов (S1, дословно): "If the two candidate rows have equal volumes, choose
   the row closer to the POC. If the distances are equal, choose the row above the POC."
8. VAH = верхняя включённая строка, VAL = нижняя.

**⚠ Это НЕ классический CBOT-метод.** Классика Market Profile сравнивает СУММЫ ПАР строк
(две сверху против двух снизу) и добавляет пару целиком; LuxAlgo (S11) описывает именно
парный метод и отмечает: "some implementations expand one row at a time instead".
TV в своей справке (S1) описывает ПОСТРОЧНЫЙ метод — при порте копировать S1, не классику.
На одних и тех же данных методы дают РАЗНЫЕ VAH/VAL.

## 6. Fixed Range vs Visible Range (курс, стр. 63: VRVP "для удобства поиска", FRVP "для ТВХ и уровней")

Расчётная машина ОБЩАЯ (S1 — "traits shared by all Volume Profile indicators"; формула
Ticks Per Row и меню Volume совпадают в S2/S3/S4; правило "<5000 баров" одно и то же в
S2 и S4). Различия:

| | Fixed Range (S2, S3, S6) | Visible Range (S4) |
|---|---|---|
| диапазон | вручную: две точки (инструмент рисования) или два бара (индикатор) | ВСЕ видимые на экране бары; пересчёт при каждом скролле/зуме |
| стабильность | фиксирован — уровень воспроизводим | плывёт вместе с экраном — POC/VA меняются от прокрутки |
| intrabar ТФ | зависит от ширины ВЫБРАННОГО диапазона (<5000 баров) | зависит от ширины ЭКРАНА — тот же алгоритм, другой вход |
| Extend Right | есть (S2: профиль продолжает включать новые бары справа) | не нужен — экран и так живой |
| форм-фактор | и индикатор, и инструмент рисования | индикатор |

Следствие для порта: ОДНА функция `profile(bars_ltf, range, rows_layout, row_size,
va_percent)`; FRVP и VRVP — два способа подать `range`. Курсовой сценарий (FRVP по
границам накопления) воспроизводим точно, потому что диапазон фиксирован.

## 7. Развилка: "побитово как TV" против "вернее TV"

У нас кэш СДЕЛОК — данные точнее минутных баров TV.

* **Побитово как TV** требует: (а) агрегировать сделки в OHLCV младшего ТФ по правилу
  "<5000 баров" из п. 2 — воспроизводимо точно; (б) разложить объём бара по строкам —
  а ЭТОТ шаг TV не документирует (п. 2), сообщество расходится (равномерно /
  пропорционально / по close). Значит побитовость по открытым источникам НЕДОСТИЖИМА —
  только калибровкой против живого TV (наложить наши числа на их профиль на одном
  диапазоне и подобрать правило раскладки).
* **Вернее TV:** класть в строки сами СДЕЛКИ (цена сделки → строка однозначно, без модели
  распределения внутри бара) — строго точнее любой intrabar-модели; сам TV делает так
  только в футпринте на тарифах с тиковыми данными (S5). При этом сетку строк, округление
  Ticks Per Row, POC и алгоритм VA — копировать у TV дословно (пп. 1, 4, 5), потому что
  курс называет уровни ПО TV.
* Замер репозитория (04-poc-tv-emulation.md) уже показал: главный источник расхождения
  18–29% — не "тики против баров", а СЕТКА (число строк) и цена строки. Решает
  копирование пп. 1/4/5; "тики против размазывания по бару" — поправка второго порядка.
* Up/down: по сделкам честнее сторона агрессора (у нас есть) — но это ДРУГОЕ число, чем
  у TV (у них — направление минутной свечи, п. 3). Если карточка должна сходиться с
  экраном TV владельца — считать up/down по правилу TV из intrabar-баров, агрессора
  держать отдельным полем.

Решение о развилке — владельцу. Данные для решения: POC/VA почти целиком определяются
пп. 1/4/5 (копируются точно по официальной справке), недокументирован только шаг
распределения объёма внутри intrabar-бара, и при минутных барах его вклад мал.

## Чего выяснить НЕ удалось

1. **Значение Row Size по умолчанию.** Официальная справка молчит; свидетельства: "около
   100" (S8, живой TV, февраль 2026), "24…100 platform dependent" (S11). Утверждение
   "24 строки" НЕ подтверждено и НЕ опровергнуто. Живая проверка не проведена: браузерная
   панель зависла (preview_start и navigate — таймаут 300 с). Как проверить: открыть
   tradingview.com/chart, инструмент "Фиксированный профиль объема", диалог настроек.
2. **Формула распределения объёма intrabar-бара по строкам** — официально не опубликована
   нигде (проверены S1–S5 дословно). Только реконструкции сообщества (равномерно /
   пропорционально перекрытию high-low). Устанавливается лишь калибровкой против живого TV.
3. **Тай-брейк ничьей POC** (не VA-кандидатов) — официально не документирован.
4. **Цена строки (низ/центр/верх)** для линии POC — официально не документирована.
5. **Противоречие close=open:** S1 — "≥ open → up", S3 — "<= open → down". Действующее
   правило устанавливается только живым экспериментом на баре-дожи.
