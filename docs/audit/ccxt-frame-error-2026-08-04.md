# Рамка поиска была неверна: я искал `watch_ohlcv`, а надо было спросить, нужен ли он вообще

**Дата:** 2026-08-04. Четвёртое уточнение. Предыдущие: `ccxt-review` (n=1), `ccxt-practice-addendum` (n=2), `ccxt-practice-survey` (n=5, три не на ccxt), `ccxt-consumers-only` (только ccxt, но рамка та же).

---

## 0. В чём ошибка рамки

Я искал по строке `watch_ohlcv`, потому что её использует hunter/exchange.py. Это **отбор по исходу**: такой запрос находит ровно тех, кто принял то же решение, что и hunter, и не находит никого, кто принял другое. Дальше я описывал найденное как «практику» и — хуже всего — объявил малое число находок свойством популяции:

> «выборка узкая не потому, что я плохо искал, а потому что популяция узкая»

Это неверно. Популяция ccxt огромна. Узкой оказалась **доля тех, кто берёт свечи вебсокетом**. Я принял хвост распределения за всё распределение, и вопрос «а надо ли вообще брать свечи по WS» ни разу не был задан — хотя это первый вопрос, который следовало задать, и он архитектурный, а не транспортный.

Ниже это измерено.

---

## 1. Замер: REST против WS в публичном коде на ccxt

Один индекс (grep.app), одинаковая методика, счётчики попаданий:

| запрос | всего | внутри `ccxt/ccxt` | **вне ccxt** |
|---|---|---|---|
| `import ccxt` | 3 923 | 1 917 | ≈ 2 006 |
| `fetch_ohlcv` | 1 436 | 451 | **≈ 985** |
| `fetchOHLCV` | 2 521 | 2 029 | **≈ 492** |
| `watch_ohlcv` | 179 | 147 | **32** |
| `watchOHLCV` | 1 213 | ≈ 1 116 | **≈ 97** |

Итого вне самой библиотеки:

* **REST-путь (`fetch_ohlcv` + `fetchOHLCV`): ≈ 1 477 попаданий**
* **WS-путь (`watch_ohlcv` + `watchOHLCV`): ≈ 129 попаданий**

**Соотношение ≈ 11 : 1 в пользу REST.**

Оговорки, которые обязаны стоять рядом с этим числом: попадания — не проекты (один репозиторий даёт десятки строк); индекс grep.app — не весь публичный код; camelCase-запросы ловят и не-Python. Но порядок величины устойчив по четырём независимым запросам, и он однозначен: **подавляющее большинство проектов на ccxt получает свечи запросом, а не подпиской.**

Из этого следует и переоценка прежнего вывода: «всего 7 репозиториев с `watchOHLCV`» — это не «мало кто пишет ботов на ccxt», а **«мало кто берёт свечи по вебсокету»**. Что само по себе является ответом на вопрос, который я не задал.

## 2. Что делают те три, кто всё-таки взял свечи по WS

Расширение рамки дало третьего настоящего потребителя — **passivbot** (я раньше отбросил его, увидев только `watch_orders`; свечи у него в отдельном модуле src/live/candle_ws.py). И у всех трёх обнаружилась одна и та же архитектура, которой у hunter нет.

### freqtrade

WS — ускоритель, REST — страховка:

```python
logger.info(f"Couldn't reuse watch for {pair}, {timeframe}, falling back to REST api.")
```

### passivbot — src/live/candle_ws.py

```python
rows = await bot.ccp.watch_ohlcv(symbol, "1m")
...
# Some venues return hundreds of cached rows on every
# update. Only the current/finalized tail can contribute
# to canonical ingestion; reconnect gaps deliberately use
# REST instead of replaying a large WS snapshot.
tail_rows = rows[-3:] if isinstance(rows, list) else rows
```

и в candlestick_manager.py:

```python
# source: Optional ingestion provenance. "ws" records the latest
#   finalized WebSocket timestamp without advancing REST refresh metadata.
...
# WebSocket rows become canonical trading inputs only after the shard
# write succeeds. A failed write must not leave restart-sensitive
# candles or EMA state visible exclusively in RAM.
```

То есть: **REST — канон, WS — живой хвост из трёх строк, дыры после обрыва закрываются REST-ом принципиально, а не по возможности.**

### opentrader

Свечи проходят насквозь, но для сделок реализован тот же приём — проверка `has[...]` и падение назад на `fetchTrades`.

### Сводка

| проект | источник свечей | роль WS |
|---|---|---|
| freqtrade | WS с откатом на REST | ускоритель |
| passivbot | **REST канонический**, WS — хвост | ускоритель |
| opentrader | WS насквозь (для сделок — REST-откат) | основной, но без гарантий |
| **hunter-v2** | **только WS** | **единственный источник** |

**Ни один из трёх не полагается на WS как на единственный источник баров. hunter — полагается.**

## 3. Что было бы, если бы hunter брал бары через REST

### 3.1. Бюджет запросов

Каждый ряд опрашивается один раз за свой таймфрейм:

| ТФ | опросов на символ в час |
|---|---|
| 5м | 12 |
| 15м | 4 |
| 1ч | 1 |
| 4ч | 0.25 |
| 1Д | 0.042 |
| 1Н | 0.006 |
| **итого** | **≈ 17.3** |

× 27 символов = **≈ 467 запросов в час ≈ 0.13 запроса в секунду.**

Вес `klines` по внутренней таблице ccxt 4.5.70 — 1 (для малых лимитов 0.4). Даже если взять пессимистичную оценку веса 10 за запрос на `limit=1000`, получается 4 670 единиц веса в час = **78 в минуту при лимите Binance порядка 2 400/мин, то есть около 3% бюджета.**

⚠ Официальную таблицу весов Binance по лимиту я подтвердить не смог: `WebFetch` на страницу документации вернул главную вместо раздела. Число 2 400/мин взято из общеизвестных значений и **требует проверки владельцем**; вывод «запас на порядок» устойчив к ошибке в этом числе в несколько раз.

Для сравнения: сегодняшний засев уже делает **162 REST-запроса за один прогон**, то есть механика и бюджет в проекте проверены на практике.

### 3.2. Что исчезает вместе с WS-баровым слоем

| находка прежних отчётов | судьба |
|---|---|
| Д-1 — счётчик незакрытых свечей тождественно ноль | **исчезает**: REST отдаёт снимок, «последняя формирующаяся» определяется однозначно |
| Д-2 — бар может быть отдан с непоследними значениями (задержка `x=true` до 3 с) | **исчезает**: у снимка нет «ожидающего окончательного обновления» |
| Д-3 — разрывы не пересчитываются на WS-фазе | **исчезает**: каждый ответ REST — цельный ряд, разрывы видны сразу |
| Д-6 — пропущенное за обрыв не докачивается | **исчезает**: следующий опрос отдаёт последние N баров независимо от того, что было |
| Д-11 / C-1 — 47.00 с разгона подписок | **сокращается**: остаются 27 подписок на сделки ≈ 7 с |
| C-5 — порог тишины на барах | **исчезает** для баров |
| C-9 — запас до лимита 200 подписок 11 штук | **исчезает**: 27 вместо 189 |
| Р-2 — «2 свечи» считаются индексами списка | **не исчезает**, но перестаёт усугубляться дырами от обрывов |

Восемь находок из слоя данных снимаются не исправлением, а **удалением подсистемы**.

### 3.3. Что теряется

* **Задержка.** Сигнал на закрытии 5м-бара будет замечен на следующем опросе: задержка ≈ RTT плюс джиттер планировщика, порядка 1–2 с вместо «сразу». Для метода, где младшие ТФ по §2.8 нужны «только для тайминга входа», а оператор торгует руками (§1), это не имеет значения.
* **Наблюдение внутри свечи.** Проекту оно не нужно: весь расчёт §2 работает по закрытым барам.
* **«Живость» прогона `hunter check`.** Проверка свежести данных на REST выражается даже проще — сравнением метки последнего бара с ожидаемой границей.

### 3.4. Что WS обязан остаться

**Сделки (aggTrade) — да, безусловно.** Это измерено самим проектом: REST отдаёт 1000 сделок за 0.45–1.69 с, покрывая 51–110 с рынка; сутки — около 1440 запросов и ~36 минут. Профиль объёма §2.2 без потока сделок не построить. То есть WS-сложность в проекте **заслужена ровно там, где она заслужена**, и не заслужена на барах.

Итоговая конфигурация: **27 WS-подписок на сделки + REST-опрос баров + суточный архив для истории.** Против нынешних 189 подписок.

## 4. Что расширение рамки дало сверх этого

Подтверждение находки C-6 из производственного кода. passivbot/src/live/candle_ws.py:

```python
"""Unsubscribe while the watcher still owns CCXT's subscription future.

CCXT Pro uses ``UnsubscribeError`` to wake outstanding ``watch_ohlcv``
futures after an unsubscribe acknowledgement.  Cancelling Passivbot's
awaiting task first leaves that future orphaned, which asyncio later logs
as ``Future exception was never retrieved``.
"""
```

`UnsubscribeError` — один из двух классов, которые `hunter._watch_step` **не ловит** (наследуется от `BaseError` напрямую, минуя `NetworkError` и `ExchangeError`). Здесь он назван боевым проектом как штатный механизм пробуждения ожидающих `watch_ohlcv`. То есть это не гипотетический класс из дерева наследования, а то, что реально прилетает.

Плюс у passivbot: `except Exception` катч-олл, экспоненциальная задержка `reconnect_delay_seconds(consecutive_failures)`, и `clear_live_ws_ohlcv_state(symbol)` при ошибке — очистка кэшированного состояния, как `_pop_history` у freqtrade.

С passivbot число настоящих потребителей `watch_ohlcv` из ccxt стало **три** (freqtrade, OctoBot, passivbot), то есть §0.1 «минимум три независимых источника» для ccxt-специфичных пунктов теперь формально выполним — но это уже неважно, потому что главный вывод сменился: **вопрос не «как правильно брать свечи по WS», а «зачем брать их по WS».**

## 5. Пересобранная рекомендация по слою данных

**Было** (три предыдущих документа): реализовать правило преемника, батч-подписку, катч-олл ошибок, откат на REST, суточный сброс соединений — то есть чинить WS-баровый слой.

**Стало:**

1. **Снять бары с вебсокета.** Опрашивать `fetch_closed_ohlcv` по расписанию, привязанному к границам ТФ. Функция уже написана, `since_ms` уже поддержан, бюджет запросов — около 3% лимита.
2. **Оставить WS только на сделках** — 27 подписок, разгон ≈7 с вместо 47 с, и это единственное место, где WS доказанно необходим.
3. **Из прежних рекомендаций сохраняют силу только те, что касаются оставшегося потока сделок**: ловить `ccxt.BaseError` (включая `UnsubscribeError` — подтверждено passivbot), не зацикливать `BadRequest`, закрывать соединение явно при сетевом сбое, очищать состояние символа при ошибке, вынести приём из общего цикла.
4. **Правило закрытия свечи** становится неактуальным для баров и не нужно для сделок. Это самый крупный результат расширения рамки: три документа обсуждали задачу, которую можно не решать.
5. **Замер, который стоит сделать до правки**: прогнать сутки параллельно — WS-бары против REST-баров того же символа и ТФ — и посчитать, сколько раз они разошлись и на сколько. Это ответит на вопрос «а что мы теряем» числом, а не рассуждением, и по §0.1 будет источником уровня 1.

## 6. Что осталось непроверенным

1. **Счётчики grep.app — это строки, а не проекты**, и индекс не покрывает весь публичный код. Соотношение 11:1 — оценка порядка, а не измерение доли проектов.
2. **Официальная таблица весов Binance для `klines` не подтверждена** — WebFetch отдал главную страницу документации вместо раздела. Расчёт бюджета опирается на таблицу ccxt (вес 1 / 0.4) и на общеизвестное 2 400/мин.
3. **Не проверено, как REST-опрос ведёт себя на границе ТФ** — успевает ли Binance закрыть свечу к моменту первого запроса после границы, или нужен отступ. Это ровно тот же вопрос задержки, что и с `x=true`, и он требует живого замера. Возможно, потребуется опрашивать с задержкой в несколько секунд после границы.
4. **passivbot прочитан частично**: candle_ws.py целиком, candlestick_manager.py (438 КБ) — только по грепу.
5. **Не сравнивались данные**: расходятся ли фактически бары из WS и из REST на одном символе. Пункт 5 раздела 5 — это и есть недостающий замер.
6. **`fapi.binance.com` из этого окружения недоступен** (`HTTP 451`), поэтому ничего из перечисленного не проверено на живом соединении.
