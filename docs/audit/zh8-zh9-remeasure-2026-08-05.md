## 1. Ж-8. Перемер леджера после Н-1, Н-2 и Б-3

### 1.1. Что требовалось

Задание: «до правок замер давал средний R **+0.4813** при 54% целей из будущего. После
правок число обязано измениться; **если не изменилось — правки не сработали**».

### 1.2. Контроль: способен ли прибор ответить иначе

Обязателен по CLAUDE.md. `build_targets` зовётся ЧЕТЫРЕЖДЫ — на настоящем пуле и на трёх
подделанных, где отсев выключается подменой ДАННЫХ, а не кода:

| вариант пула | основных целей | целей всего |
|---|---:|---:|
| **как есть** (оба отсева) | **1086** | **1124** |
| без отсева по времени (Н-1) | 1731 | 2526 |
| без отсева по состоянию (Н-2) | 2069 | 2179 |
| оба отсева выключены | **2714** | **3581** |

Отсевы срезают **1086 из 2714 — 60% целей**. Совпадение первой и последней строки
означало бы, что отсев не работает; они расходятся втрое. **Контроль пройден.**

Из этого же следуют доли, которые задание просило назвать:

* **цели, созданные позже сигнала:** 1731 − 1086 = **645, то есть 37%** от того, что было
  бы без фильтра. Теперь их **0 по построению**;
* **цели в состоянии `worked_off`/`flipped` на момент сигнала:** 2069 − 1086 = **983, то
  есть 47%**. Теперь **0**.

Прежние замеры внешнего разбора — 54% и 83%. Направление то же, величины ниже: материал
другой (см. 1.5).

### 1.3. Числа после правок

Офлайн-конвейер на сохранённых кадрах, BTC и ETH, все шесть ТФ:

| | закрыто | сумма R | средний R | медиана | выигрышей |
|---|---:|---:|---:|---:|---:|
| **эмитируемые** | 19 | **+3.156** | **+0.166** | +0.155 | 11/19 (**58%**) |
| все уровни | 116 | −40.568 | −0.350 | −1.000 | 39/116 (34%) |

Живой леджер (`hunter ledger`), 59 сигналов:

    всего_советов 59 | из_них_закрыто 3 | ещё_без_исхода 56
    по_цели 1 | по_стопу 1 | неоднозначно 1
    сумма_R -0.591 | средний_R -0.296

### 1.4. Сравнение с числом до правок

| величина | до правок | после |
|---|---:|---:|
| средний R (эмитируемые) | **+0.4813** | **+0.166** |
| сумма R | +19.25 | +3.156 |
| выигрышей | 37 против 3 — **92%** | 11 против 8 — **58%** |
| медиана РР | **0.426** | **1.788** |
| доля РР ≥ 1к3 (стр. 9) | 6% (10% среди эмитируемых) | **28%** |
| медиана дистанции стопа | 0.740% | 0.684% |

**Число изменилось — правки сработали.** Прежние +0.4813 и 92% выигрышей были артефактом
целей из будущего.

**Почему РР вырос вчетверо, а доля выигрышей упала.** Это не противоречие, а одно и то же
следствие. Цель, созданная ПОСЛЕ сигнала, почти всегда лежит близко к нему — она успела
сформироваться между сигналом и исходом. Такие цели давали высокую долю попаданий при
низком РР. Убрав их, мы остались с далёкими законными целями: РР 0.426 → 1.788, попадания
92% → 58%. Обе величины сдвинулись именно так, как обязано было сдвинуться при снятии
заглядывания вперёд.

### 1.5. Что это число НЕ означает

**Комиссии съедают почти всё.** При медианном стопе 0.684% цены круговая комиссия тейкера
0.10% составляет **0.146 R на сделку**:

| | средний R | с комиссией |
|---|---:|---:|
| эмитируемые | +0.166 | **+0.020** |
| все уровни | −0.350 | −0.496 |

**+0.02 R — это ноль в пределах шума.** Ставка 0.10% — типовая, не замер по счёту;
проскальзывание и невозможность встать в ПОК лимиткой при проходе цены насквозь не
учтены, то есть реальная цифра скорее ниже.

Прочие ограничения:

1. **Закрытых сделок 19.** На такой выборке средний R не отличим от нуля ни в какую
   сторону.
2. **Не исполнено 30 из 52 эмиссий** (58%): вход лимиткой в ПОК, и цена до него не дошла.
   Это свойство метода, а не сбой, но оно означает, что «сделок» вдвое меньше «советов».
3. **Материал не тот, что в исходном замере.** Задание называло июль 2026, BTC/ETH/DOGE/SOL,
   ТФ 15м/1ч/4ч. Здесь BTC и ETH, все шесть ТФ, горизонт 40 суток от 2026-08-05: архива по
   DOGE и SOL в кэше нет, а качать 40 суток на два символа ради полной сопоставимости
   несоразмерно замеру. Доли (37%, 47%) поэтому с 54% и 83% сравнивать нельзя напрямую;
   сопоставимо только НАПРАВЛЕНИЕ.
4. **Полная популяция убыточна:** −0.350 R, 34% выигрышей на 116 сделках. Положителен
   только эмитируемый отбор. Это согласуется с находкой Б-2а (отбор УЛУЧШАЕТ выборку), но
   означает, что ценность создаёт фильтр эмиссии, а не сам уровень.
5. **Живой леджер бесполезен для суждения:** 3 закрытых исхода из 59 сигналов. Это прямое
   следствие правки Б-3 — исход считается только по барам, закрывшимся ПОСЛЕ записи
   сигнала, и переигранная история больше не порождает мгновенных исходов.

## 2. Ж-9. Сверка с разметкой автора на пятиминутной корзине

### 2.1. Что требовалось

`author-poc-2026-08-04.md` мерился на **15-минутной** корзине кэша, код перешёл на
**5-минутную** (`CACHE_BUCKET_MS = 300_000`). Задание: перемерить и отдельно проверить,
что окна структур 5м ложатся на сетку корзин без округления.

### 2.2. Выравнивание окон — проверено и застраховано

Замер кратности шага ТФ размеру корзины:

| корзина | 5м | 15м | 1ч | 4ч | 1Д | 1Н |
|---|---|---|---|---|---|---|
| 300 000 (сейчас) | **кратен** | кратен | кратен | кратен | кратен | кратен |
| 900 000 (прежняя) | **НЕ кратен** | кратен | кратен | кратен | кратен | кратен |

То есть дефект был реален: на прежней корзине окна 5м-структур округлялись молча, пока
протокол утверждал «срез точен». На нынешней корзине кратны все ТФ вселенной, и
округления нет.

В `probes._histogram_over` добавлена проверка выравнивания: невыровненное окно теперь
даёт `NotReady`, а не молча округлённый срез. Контроль:

| окно | результат |
|---|---|
| `[0, 600000)` — на сетке | `TradeHistogram` |
| `[0, 500000)` — правая граница вне сетки | `NotReady`: не на сетке корзин |
| `[100000, 600000)` — левая граница вне сетки | `NotReady`: не на сетке корзин |

Прогон зонда с включённой страховкой дал те же числа, что без неё, — то есть ни одно
реальное окно её не задело. Это и ожидалось из таблицы кратности; проверка оставлена на
случай следующей смены корзины.

### 2.3. Результат — ключевое свидетельство НЕ подтвердилось

| | 15м корзина (04.08) | **5м корзина (05.08)** |
|---|---|---|
| BTC: сошлось | 8 из 20 (40%) | **7 из 20 (35%)** |
| BTC: медиана расстояния | 0.511% | **0.951%** |
| BTC: исходное лучше сдвигов | 45 из 56 → ранг 12/57 (p≈0.21) | **16 из 56 → ранг 41/57 (p≈0.72)** |
| ETH: сошлось | 7 из 16 (44%) | **7 из 16 (44%)** |
| ETH: медиана расстояния | 0.264% | **0.264%** |
| ETH: исходное лучше сдвигов | 55 из 56 → ранг **2/57 (p≈0.035)** | **46 из 56 → ранг 11/57 (p≈0.19)** |

**Контроль-решётка на 5м корзине:**

| | у автора | решётка N | решётка 4N |
|---|---|---|---|
| BTC: сошлось / медиана | 35% / 0.951% | **40% / 0.823%** | 28% / 0.651% |
| ETH: сошлось / медиана | 44% / 0.264% | **50%** / 0.307% | **48%** / 0.304% |

### 2.4. Что из этого следует

**Единственное статистически значимое наблюдение проекта исчезло.** ETH давал ранг 2 из
57 (p≈0.035) — на 5-минутной корзине это ранг 11 из 57, **p≈0.19**. Порог значимости не
пройден ни на одном символе.

**BTC стал хуже случайного:** исходное положение разметки лучше лишь 16 сдвигов из 56.
На 15-минутной корзине было 45 из 56. Смена корзины перевернула знак.

**Произвольная решётка снова обходит автора по доле совпадений** на обоих символах — то
есть возвращается ровно тот дефект, который `author-poc` в своё время у себя же нашёл и
объяснил избытком уровней. Отсев по состоянию его тогда снял; на 5м корзине он вернулся.

Утверждение «разметка автора и наши активные ПОК связаны» на нынешнем коде **не
подтверждается**. Это не опровержение метода — это отсутствие свидетельства в его пользу.

⚠ Чего замер НЕ говорит: он не показывает, какая корзина правильнее. 15-минутная давала
более сильный результат, но именно на ней окна 5м округлялись молча (2.2), то есть её
числа получены прибором с известным дефектом. Пятиминутная корзина этого дефекта не
имеет. Значит верить надо ей, а не той, где число красивее.

## 3. Как перепроверить

```bash
# Ж-8: контроль отсева, исходы, РР и R
uv run python -m hunter run --run-id last --symbols 2 --seed-limit 1000 \
    --seconds 20 --horizon-days 40
uv run python scripts/probes.py emit-quality

# Ж-9: сверка с автором на нынешней корзине
uv run python scripts/probes.py author-poc

# кратность шага ТФ размеру корзины — почему прежний замер округлялся
uv run python -c "
from hunter.bars import TIMEFRAME_MS
from hunter.archive import CACHE_BUCKET_MS
for tf, ms in TIMEFRAME_MS.items():
    print(tf, ms, 'кратен' if ms % CACHE_BUCKET_MS == 0 else 'НЕ кратен', CACHE_BUCKET_MS)
"

# страховка выравнивания срабатывает
uv run python -c "
import sys; sys.path.insert(0, 'scripts')

from decimal import Decimal

f = [pl.DataFrame({'bucket':[0],'bin':[1],'qty':[1.0],'n':[1]})]
for lo, hi in ((0,600000),(0,500000),(100000,600000)):
    print(lo, hi, type(_histogram_over(f,'T',Decimal('0.1'),lo,hi)).__name__)
"
```
