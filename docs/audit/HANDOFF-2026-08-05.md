Случаи гейта, прямо соответствующие находкам:

* `c_two_candles_are_time_not_index` — ряд с дырой, возврат следующим по списку баром обязан дать `UNRESOLVED`, а не `PUNCTURE`. **Р-2 закрыт.**
* `c_target_not_from_future` — цель, рождённая позже сигнала, отбрасывается. **Н-1 закрыт.**
* `c_target_not_retired` — снятый уровень целью не является. **Н-2 закрыт.**
* `c_target_retired_later_still_counts` — **поправка к моей же рекомендации.** Фильтровать цели по СЕГОДНЯШНЕМУ состоянию значило бы заменить одно заглядывание вперёд другим; фильтр обязан сравнивать `resolved_at_ms` с моментом сигнала. Я этого не оговорил, автор правки — оговорил. Это лучше моей формулировки Н-2.
* `c_outcome_only_future_bars` — `first_bar_after(b, TF, since, not_before=1) == 3`. **Б-3 закрыт по существу**: исход больше не считается по барам, существовавшим до записи сигнала.

Ветка при умолчании остаётся мёртвой. Решение защитимое; фиксируется как известное.

`gates/binning_agrees.py` — поведенческий гейт по **12 шагам цены × 5 000 узлов сетки**, три ветви (скалярная, полярисовая, точная десятичная). Третья ветвь добавлена именно затем, чтобы гейт не проверял «две реализации ошибаются одинаково». **Б-1 закрыт правильно.**

## 4. Главная нерешённая задача: слой биржи

exchange.py не менялся, и по нему получен вывод, меняющий не реализацию, а **состав системы**.

### 4.1. Замер, который меняет постановку

Поиск по индексу публичного кода, вне репозитория ccxt:

| путь | попаданий |
|---|---:|
| `fetch_ohlcv` + `fetchOHLCV` (REST) | **≈ 1 477** |
| `watch_ohlcv` + `watchOHLCV` (WS) | **≈ 129** |

**≈ 11 : 1 в пользу REST.** Подавляющее большинство проектов на ccxt получает свечи запросом, а не подпиской.

Из трёх настоящих потребителей `watch_ohlcv` (freqtrade, OctoBot, passivbot) **ни один не полагается на WS как на единственный источник баров**:

* freqtrade — `«Couldn't reuse watch … falling back to REST api»`;

* opentrader — проверка `has[...]` и откат на `fetchTrades`.

hunter — полагается.

### 4.2. Арифметика REST-опроса баров

Каждый ряд опрашивается раз за свой ТФ: 5м 12/ч + 15м 4 + 1ч 1 + 4ч 0.25 + 1Д 0.042 + 1Н 0.006 ≈ **17.3 опроса на символ в час** × 27 символов = **≈ 467 запросов в час ≈ 0.13 запроса в секунду**. Даже при пессимистичной оценке веса 10 за запрос это ≈78 единиц веса в минуту против лимита порядка 2 400/мин — **около 3% бюджета**. Засев уже сейчас делает 162 REST-запроса за прогон, то есть механика проверена.

### 4.3. Что исчезает вместе с WS-баровым слоем

Д-1, Д-2, Д-3 (в части WS-фазы), Д-6, Д-9, Д-10, C-1/Д-11 (47 с → ≈7 с на 27 подписках), C-2, C-5, C-8, C-9. **Одиннадцать позиций снимаются удалением подсистемы, а не правкой.**

### 4.4. Что WS обязан остаться

**Сделки (aggTrade).** Замерено самим проектом: REST отдаёт 1000 сделок за 0.45–1.69 с, покрывая 51–110 с рынка; сутки ≈1440 запросов и ~36 минут. Профиль §2.2 без потока сделок не построить.

**Целевая конфигурация: 27 WS-подписок на сделки + REST-опрос баров + суточный архив для истории.** Против нынешних 189 подписок.

Don't loop`); закрывать соединение явно при сетевом сбое (2 из 2 потребителей ccxt); очищать состояние символа при ошибке; вынести приём из общего цикла; проверять `exchange.has[...]` перед подпиской (3 из 5 проектов, у hunter нет нигде).
