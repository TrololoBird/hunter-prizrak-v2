Наш модуль — `src/hunter/breach.py`, требование — FOUNDATION §2.4. Здесь живёт

### Семейство C — с ПОРОГОМ ГЛУБИНЫ и окном (1 проект)

MQL5, статья «Turtle Soup Liquidity Sweeps» (Part 50) — исходник опубликован в статье.
Три приёма, которых у нас нет ни одного:

**1. Порог глубины прокола** — заход обязан быть достаточно глубоким И в пунктах, И в
процентах от диапазона:

```cpp
bool sellDepthPasses = (!InpUseSweepDepthFilter)
  || (sellSweepDepth >= InpMinSweepDepthPoints * _Point
      && (sellSweepDepth / lookbackRange * 100.0) >= InpMinSweepDepthPctRange);
```

**2. Возврат подтверждается НЕСКОЛЬКИМИ закрытиями**, а не одним баром:

```cpp
bool AllConfirmClosesInsideLevel(bool checkBelowLevel, double referenceLevel, int barsToConfirm)
{
  for(int barIdx = 1; barIdx <= barsToConfirm; barIdx++)
  {
    double closePrice = iClose(_Symbol, InpSignalTimeframe, barIdx);
    if(checkBelowLevel) { if(!(closePrice < referenceLevel)) return false; }
    else { if(!(closePrice > referenceLevel)) return false; }
  }
  return true;
}
```

**3. Окно захода задаётся параметром** (`InpSweepWindowBars`), классический вариант — 1 бар.

### Три вещи, которые обзор сказал про наш открытый вопрос М-15

Напомню напряжение: текст стр. 6 даёт окно возврата «той же или следующей 1-2 свечами»,
надпись на схеме той же страницы говорит «Во всех случаях - цена не уходит за уровень
целыми свечами». Реализовано по тексту.

**1. Многобарный прокол в чужих реализациях СУЩЕСТВУЕТ.** Индикатор False Breakouts на
TradingView (исходник закрыт, потому не засчитан) описывает три вида, третий — «price
breaks a level and holds beyond it for several bars (limited by Max Hold Bars setting)
before sharply reversing». То есть параметр «сколько баров можно простоять за уровнем»
кто-то заводит явно.

**2. Но и однобарное чтение представлено:** классический Turtle Soup, по описанию самой
статьи MQL5, использует окно в ОДИН бар (`InpSweepWindowBars`, значение по умолчанию 1).

**3. Никто не решает это через свойство «нет целых свечей за уровнем».** Все, кто
ограничивает, ограничивают ЧИСЛОМ БАРОВ, а не отсутствием тел. То есть прочтение схемы,
которое я пробовал внести и которое откатил гейт, в выборке не встречается ВООБЩЕ.

⚠ Это не разрешает М-15 — курс остаётся единственным арбитром, а поле про него ничего не
знает. Но оно снимает довод «так делают все»: не делают. Напряжение остаётся находкой.

### Наша особенность, которой нет ни у кого

**`UNRESOLVED` — третий исход «источник вердикта не даёт».** Ни один из семи проектов

Это прямое следствие §4.3 (не подставлять значение вместо отсутствующего) и записано в

### Р1 — порог глубины не нужен, и нуль сказал больше, чем порог

Глубина захода за уровень: медиана **2.108 ATR**, минимум 0.0008, максимум 81. Мельче
десятой доли ATR — только 4.0% событий, то есть мелкие проколы, ради которых чужие проекты
заводят порог, у нас редки. По порогу, названному до прогона, — закрыть.

**Нуль сказал больше.** На решётке ПРОИЗВОЛЬНЫХ равноотстоящих цен вместо уровней проекта:
3706 событий против 3682, медиана глубины 3.091 ATR, мельче 0.1 ATR — 2.8% против наших
4.0%. **Распределения практически совпали.** Значит глубина захода мерит ВОЛАТИЛЬНОСТЬ, а
не свойство уровня, и порог по ней не отобрал бы ничего осмысленного — он резал бы одинаково
и настоящие уровни, и произвольные цены.

Нуль при этом свойство ломает — число событий отличается (3706 против 3682), то есть
сравнение законно.

⚠ Это второй раз за день, когда решётка произвольных цен показывает, что величина
принадлежит рынку, а не разметке. Первый был в замере конформанса.

### Р2 — определение возврата меняет исход у четверти событий

| исход | наш (бар целиком по эту сторону) | их (закрытие по эту сторону) |
|---|---:|---:|
| пробой | 2297 | **2685** |
| прокол | 991 | 965 |
| **вердикта нет (`UNRESOLVED`)** | **394** | **0** |
| события нет вовсе | 0 | 32 |

Различается **1033 события из 3682 (28.1%)**, затронуты все 18 рядов.

**Главное в этой таблице — нижняя строка.** При возврате по закрытию наш третий исход
`UNRESOLVED` исчезает ПОЛНОСТЬЮ. Он существует не сам по себе, а как следствие строгого
определения возврата: пока бар задевает уровень тенью, событие у нас не кончилось, и часть
таких событий уходит за окно прокола, не набрав тел.

**Почему пробоев у них больше, хотя возврат засчитывается раньше.** Наше правило начинает
заход на ПЕРВОЙ же тени за уровнем; их — только когда бар за уровнем ЗАКРЫЛСЯ. Ранние
заходы одной тенью мы считаем отдельными событиями (и чаще проколами), а они их пропускают
и классифицируют уже настоящий толчок. То есть два определения классифицируют РАЗНЫЕ
события, а не одно и то же по-разному.

### ⚠ Контроль К-1 для Р2 оказался слабым, и это сказано вслух

Подсаженный ряд (бар закрывается внутри, но задевает уровень тенью) дал ОДИНАКОВЫЙ исход у
обоих определений — `puncture` и там, и там. Расходятся они на нём не видом события, а
БАРОМ разрешения (третий против второго), а зонд сравнивал только вид.

Контроль «прибор способен ответить иначе» при этом пройден, но не подсадкой, а самими
данными: 1033 события из 3682 дают разный вид исхода. Синтетический случай был выбран
неудачно, и полагаться надо на замер.

## Фаза 6. Решение

**Р1 — закрыто.** Порог глубины прокола не вводим. Мелких проколов 4.0%, а нуль показал,
что глубина принадлежит волатильности, а не уровню. Приём чужих проектов не берём, и
теперь у этого есть число.

**Р2 — решение владельца.** Меняет расчёт и, что важнее, меняет СОСТАВ событий: 28.1%
исходов, полное исчезновение третьего исхода. Предъявляю выбор:

| | оставить как есть | перейти на возврат по закрытию |
|---|---|---|
| **что считается событием** | заход начинается с первой тени за уровнем | заход начинается с первого ЗАКРЫТИЯ за уровнем; ранние тени игнорируются |
| **третий исход** | 394 события честно помечены «вердикта нет» | исчезает: всё становится проколом или пробоем |
| **соответствие курсу** | стр. 46 «прокол тенью» — тень является событием | тень не событие; стр. 46 придётся перечитать |
| **соответствие полю** | так делают 3 из 7 | так делают 4 из 7 |

⚠ Моя рекомендация — **оставить**, и вот почему. Переход убирает `UNRESOLVED`, а это
единственное место в проекте, где система отказывается классифицировать при отсутствии
правила (§4.3). Купить за это соответствие большинству в четыре голоса против трёх —
плохой обмен. Но это решение владельца, а не аудита.

**Приёмов из обзора не взято ни одного.** Порог глубины отвергнут замером, допуск на
равенство уровней (`range_percent` у smart-money-concepts) относится к построению уровней,
а не к проколу, и уйдёт в обзор элемента 8.

### Что это говорит про наш открытый вопрос М-15

Напомню: текст стр. 6 даёт окно «той же или следующей 1-2 свечами», надпись на схеме той
же страницы — «цена не уходит за уровень целыми свечами», и в четвёртом нарисованном
примере цена стоит за уровнем три-четыре свечи.

**Три независимых источника по описанию заявляют окно ЗНАЧИТЕЛЬНО ШИРЕ двух свечей:**
десять баров по умолчанию у одного, параметр «сколько баров можно простоять» у второго,
«briefly … quickly recovers» без жёсткого числа у третьего. То есть многобарный прокол —
не экзотика, а норма области.

⚠ **И это по-прежнему НЕ разрешает М-15.** Арбитр — курс, а не поле; чужие проекты нашего
источника не читали. Но довод «схема противоречит здравому смыслу области» больше не
работает: она ему как раз соответствует, а наши две свечи — самое узкое окно из всех
встреченных. Напряжение остаётся находкой и решением владельца.

### Новый вопрос, которого не было в фазе 0

**Объём как подтверждение.** Обе реализации Вайкоффа требуют, чтобы заход за уровень шёл
на повышенном объёме. У нас объём в `breach.py` не участвует вовсе. В список вопросов это
не входило; записано как П12 с пометкой «мало данных» — кандидат в следующий круг.
