## 1. Восемнадцать отказов связи, невидимых нашим приборам

Журнал живого бота за первый час содержит 70 строк, из них **18 — отказы получения
обновлений**:

```
Failed to fetch updates - TelegramNetworkError: HTTP Client says -
  ClientConnectorError: Cannot connect to host api.telegram.org:443 ssl:default
  [Превышен таймаут семафора]
```

Пока идёт такой отказ, бот **глух**: сообщения пользователей не забираются. Он их не
теряет (Telegram держит очередь), но отвечает с задержкой, и снаружи это неотличимо от
«бот сломался».

**Почему это критично для НАС, а не для Telegram:** строки пишет собственный логгер
aiogram. Наш `log.degraded()` их не считает, `log.degraded_count()` о них не знает, и
сводка при остановке напечатает «сообщений потеряно 0» при восемнадцати отказах связи.
То есть прибор показывает здоровье там, где его нет, — форма дефекта, которую CLAUDE.md
называет главной.

Воспроизведение: `Select-String 'Failed to fetch updates' <журнал бота>`.

## 2. Запрос пользователя не трассируется

За тот же час бот обслужил живой запрос — это видно ТОЛЬКО по побочному следу сборки:

```
[info] сборка по запросу начата     горизонт_суток=180 символ=BTW/USDT:USDT
[info] сборка по запросу завершена  секунд=175.5 символ=BTW/USDT:USDT уровней=89
```

Чего в журнале нет ни одной строкой: кто спросил, что именно написал, в каком чате, как
текст разобрался в символ, сколько заняла отправка, **дошёл ли ответ**. Если бы отправка
упала, в журнале была бы только сборка — и выглядело бы это как успех.

Отдельно: путь «ответ по монете ВСЕЛЕННОЙ» не оставляет следа вообще никакого — там нет
сборки, а значит нет и той единственной строки, по которой сейчас видно, что бота о
чём-то спросили.

## 3. Счётчики есть, но печатаются в момент, который не наступает

`Delivery` считает ответы, неопознанные тикеры, отказы по паузе, сборки, потерянные
сообщения и ожидания по лимиту. Всё это печатается **в `finally` при остановке
polling**. Бот 24/7 не останавливается, значит числа не печатаются никогда.

## 4-6. Сообщение: чем оно стало и чем должно быть

Вот что ушло в канал по BTC (первые строки, полностью — 44 строки, 3282 знака):

```
👑 BTC — карта уровней hunter
активных уровней 69, из них лимитками торгуются 5; остальные цена уже трогала
(стр. 25); снятых уровней на графике 179

Лонги:
  🟢 60751.2–64100 (ПОК 60800) · 1d ⚠ правило входа не записано (строка карты до схемы 6)
  🟢 63670.8–64397.4 (ПОК 64094.7) · 4h ⚠ правило входа не записано (строка карты до схемы 6)
  ...
```

**Что здесь неверно по существу, а не по вкусу:**

* **«строка карты до схемы 6»** — это версия схемы SQLite. Она напечатана **30 раз** в
  одном сообщении публичного канала. Пометка нужна — но ВЛАДЕЛЬЦУ в логе, а не читателю;
* **«стр. 25», «§2.2», «hunter»** — внутренние ссылки проекта и его кодовое имя;
* **НЕТ ТЕКУЩЕЙ ЦЕНЫ.** Замер: цена BTC 63 459.9, уровни от 60 000 до 81 000. Читатель не
  может понять, какие из них близко. У автора курса цена названа в каждом посте;
* **порядок бесполезен.** Уровни отсортированы по таймфрейму и цене, а не по расстоянию
  до цены. Ближайший уровень (+0.01%) стоит пятой строкой, а первым — уровень в 5% от цены;
* **объём.** 69 активных уровней; из них 53 попадают в ±5% от цены, 10 — дальше 20%, то
  есть их не видно даже на графике. Автор в разборе называет **четыре-пять зон**:
  «61500-62000 (🟡 по факту), 60000-61000 (🟢 лимитки), 63680-63950-64360 (🔴
  сопротивление), 66600-67130 (🔴 перезакуп)» (`research/author_markup/2026-08-03_overcarder.md`);
* **«снятых уровней на графике 179»** — число, которое читателю не говорит ничего.

**Эталон формата — пост автора, а не мой вкус.** Из разметки 2026-08-03 видно устройство:
цена → несколько зон с РОЛЬЮ словами → что автор с ними делает («лимитки держу», «работать
по факту») → отметка отработанного (✅). Никаких перечней на сорок строк.

## 7. На графике 179 снятых уровней, хотя фильтр объявлен

`read_map` с 2026-08-17 отдаёт и снятые уровни — они нужны значкам отработки и отмены.
Замер по BTC: **активных 69, снятых 179**. На график 4ч попало 53 зоны, из них **31
снятая**; на 15м — 61 зона, из них 38 снятых.

⚠ Комментарий в коде утверждает: «Отбор по `retired_at` держит выборку свежей: снятое
месяц назад на график сегодняшних баров всё равно не попадёт». **В запросе нет ни одного
условия на значение `retired_at`** — только `IS NOT NULL`. То есть объявленный фильтр не
существует; отсев делает лишь `bar_index`, и то лишь для боксов структуры, а линия уровня
и значок рисуются по цене.

Видно это и глазами: на 4ч — лес из двух десятков чёрных линий, пятнадцать красных стрелок
и синих крестиков без единой подписи, ценовые плашки наезжают друг на друга
(64203.6 / 64111.2 / 63964.7 стоят подряд). На 15м одна жёлтая зона «BUY» закрывает треть
кадра. Ни на одном графике нет оси времени и отметки текущей цены.

## 8. Данные: карта старше 17 часов, у большинства символов её нет

* карта BTC на момент публикации — **1035 минут** (17 часов). В сообщении это сказано
  последней строкой мелким шрифтом, а не первой;
* карта есть у **11 символов**, из них 3 вне вселенной (`BTW`, `BEAT`, `XAU`);
  у **16 символов вселенной из 27 карты нет вовсе** — бот на них отвечает «карта пуста»;
* `data/aggcache` держит **720 МБ** кэша отдельных сделок, который после перехода профиля
  на свечи (2026-08-12) не читается ни одним боевым путём.

## 9. Молчание на 175-345 секунд

Монета вне вселенной собирается по запросу: замер сегодня — **175 с** (BTW, часть данных
уже была) и **345 с** на холодной. Бот честно предупреждает «это минуты», но между
предупреждением и ответом не подаёт ни одного признака жизни, а Telegram за это время

## Команды воспроизведения

Состояние карты, из которой строится ответ, и её отношение к текущей цене:

```bash
uv run python -c "
import asyncio
from hunter.tgbot import read_map
from hunter.exchange import Exchange
async def main():
    ex = Exchange('binanceusdm'); await ex.open()
    try:
        b = await ex.fetch_closed_ohlcv('BTC/USDT:USDT', '15m', limit=3)
        p = b.bars[-1].close
    finally:
        await ex.close()
    z = read_map('BTC/USDT:USDT').zones
    live = [x for x in z if x.state == 'active']
    lo = [x for x in live if x.side == 'long']; sh = [x for x in live if x.side == 'short']
    print('цена', p, '| активных', len(live), '| снятых', len(z) - len(live))
    print('лонгов', len(lo), 'из них ВЫШЕ цены', sum(1 for x in lo if x.price >= p))
    print('шортов', len(sh), 'из них НИЖЕ цены', sum(1 for x in sh if x.price < p))
    print('в пределах 5% от цены:', sum(1 for x in live if abs(x.price-p)/p <= 0.05))
    print('дальше 20% от цены:', sum(1 for x in live if abs(x.price-p)/p > 0.20))
asyncio.run(main())"
```

## Что из этого чинится немедленно, а что требует решения

**Чинится сразу (сделано этой правкой):**

1. трассировка запроса — строка на каждый запрос: чат, тип чата, пользователь, текст,
   разобранный символ, источник карты, длительность, доставлено ли;
2. отказы связи Telegram — считаются нашим прибором и попадают в сводку;
3. периодическая сводка живого бота, а не только при остановке;
4. формат сообщения — переписан по образцу поста автора: цена, ближайшие зоны, роли
   словами, внутренний язык убран в лог;
5. снятые уровни — реальная граница по времени вместо объявленной.

**Требует решения владельца (не делаю сам):**

* **графики.** Их переписывает параллельная правка (боксы структуры, стрелки, крестики).
  Мои замечания — лес линий, отсутствие легенды, наезжающие плашки, нет оси времени и
  отметки цены — относятся к ней, и чинить её поверх чужой незакоммиченной работы значит
  устроить конфликт. Скажете — сделаю;
* **сколько зон показывать.** Взял пять на сторону, как у автора; число можно менять;
* **что делать с 16 символами без карты** — это прогон службы, он идёт;
* **удалять ли 720 МБ мёртвого кэша сделок.**
