## Что реализовано

`volume_profile.build_tv()` — профиль по сетке TV поверх нашей тиковой гистограммы:

* **сетка** — режим Number of Rows дословно по справке: высота строки в тиках =
  round(диапазон/строки/тик), фактических строк может выйти больше заданного;
* **Value Area 70%** — построчный алгоритм справки TV (НЕ парный CBOT): большая из
  соседних строк; ничья → ближняя к ПОК; равное расстояние → верхняя; строка,
  переваливающая цель, не добавляется;
* **раскладка объёма — ПО СДЕЛКАМ** (решение, названное вслух): TV кладёт объём баров
  младшего ТФ (первый из лестницы 1м…1Д, дающий < 5000 баров) и нигде не документирует,
  как объём одного бара делится по строкам; наш кэш сделок раскладывает точнее прибора;
* **цена строки — центр** (у TV не документирована; замер E-070: центр даёт наилучшее
  согласие);
* **ничья ПОК → NotReady** (§4.3; справка молчит);
* объём вне переданного диапазона прижимается к крайним строкам и СЧИТАЕТСЯ
  (`clamped_volume`) — молча не пропадает.

Дымовая проверка (сетка, VA-останов до перевала, прижатие, вырожденный диапазон):

```bash
uv run python - <<'EOF'
from decimal import Decimal
from src.hunter.models import TradeHistogram, NotReady
from src.hunter.volume_profile import build_tv
import random
h = TradeHistogram(symbol='TEST', tick_size=Decimal('0.01')); random.seed(1)
for i in range(1000): h.add(round(100.50 + random.gauss(0, 0.12), 2), 1.0, 1000+i)
h.add(99.90, 5.0, 2000)
p = build_tv(h, bottom=Decimal('100.00'), top=Decimal('101.00'), rows=24)
assert p.ticks_per_row == 4 and p.rows_built == 25 and p.clamped_volume == 5.0
assert p.covered_volume/p.total_volume <= 0.70
assert isinstance(build_tv(h, bottom=Decimal('101.00'), top=Decimal('100.00'), rows=24), NotReady)
print('OK', p.poc_price, p.val_price, p.vah_price)
EOF
```

## ⚠ ПЕРЕКЛЮЧЕНИЕ ВЫПОЛНЕНО 2026-08-09 (вторым заходом)

Живого TradingView у владельца НЕ оказалось — вопрос Row Size закрыт заменой референта:
число строк снято с ЭКРАНА АВТОРА, то есть с нативных скриншотов самого курса (истина
№1). Зонд `probes/probe_tv_rows_2026-08-09.py`: стр. 26 — ~24 строки (шаг 5.6 px,
разрешено уверенно), стр. 36 — ~50 (шаг 5.9), стр. 33 — ≥64 и стр. 31 — ≥95 (шаг
2.2–2.5 px — предел разрешения скриншота, счёт есть нижняя граница). **Единого
умолчания у автора нет** — он либо меняет настройку от структуры к структуре, либо
работает в режиме Ticks Per Row. Взято `TV_ROWS = 100`: нижняя граница стр. 31 (ключевая
страница построения уровня двумя линиями), живой TV 02.2026 «около 100», старшая из 13
реимплементаций (MarcosACH). `levels.build_level` строит профиль `build_tv` по границам
структуры; прокольные сделки за границами прижимаются и считаются. Дифф повтора:
~2850 строк — ПОК и зоны всей карты уровней пересчитаны сеткой прибора. Чувствительность
к N остаётся замеренной (E-070) и пересматривается одной константой.

*Дополнено 2026-08-10, ОТОЗВАНО в тот же день: первый замер по кадру 44:00 («шаг
4 px, ~95-100 строк») опровергнут полным покадровым проходом — автокорреляция шага
строк с кросс-контролем на втором кадре даёт шаг 7 px, ~1.36 USD на строку (~0.07%
цены), видимых строк ~56. Прежний замер считал зазор между строками отдельной строкой.
Инвариант экрана автора — ЦЕНА строки, не число строк: довод в пользу режима Ticks Per
Row. TV_ROWS = 100 остаётся на прежних референтах (стр. 31 ≥95, живой TV 02.2026,
старшая реимплементация); видео его больше НЕ подпирает, и это сказано вслух. Разбор:
author-review-2026-08-09-vs-bot.md, третий заход.*

*Продолжение 2026-08-10: прибор научился ОБОИМ режимам Row Size (`build_tv` принимает
ровно один из `rows`/`ticks_per_row`), цена выбора замерена — при цене строки 0.07%
расхождение с боевым режимом превышает допуск 0.10·ATR у 18.3% из 665 структур. Боевой
режим НЕ меняется: за `TV_ROWS = 100` три источника, за Ticks Per Row один, а замер их
различить не способен — контроль сдвига сетки на полстроки провален (сдвинутая согласуется
не хуже честной). Разбор и числа: [`row-size-decision-2026-08-10.md`](row-size-decision-2026-08-10.md).*

## Почему боевой расчёт уровней ЕЩЁ не переключён — и что нужно от владельца (история)

**1. Число строк.** Прежнее допущение «24 по умолчанию» официальной справкой НЕ
подтверждено: Trader Dale по живому TV (февраль 2026) называет «около 100», LuxAlgo —
«24…100, зависит от платформы». По §0 величина без референта не пишется; замер E-070
показал, что от N зависит сам ответ (совпадение с тиковым ПОК 20.4% при 24 против 2.8%
при 100 на раскладке по барам). **Снять значение с живого TradingView владельца** — одна
минута: открыть настройки «Фиксированный профиль объема» → Row Size.

*Дополнено сверкой с 13 питон/Pine-реализациями (`vp-python-projects-2026-08-09.md`):
умолчания «в природе» нет — пять проектов с фиксированным числом строк дают пять разных
чисел (100, 50, 50, 24, 20), остальные задают шаг цены (как наш боевой `build()`).
Вероятный ИСТОЧНИК фольклора «24» найден: коммьюнити-скрипт ApexFlow с «default 24».
Решение `build_tv(rows=...)` без умолчания выборкой подтверждено; рабочая гипотеза для
живого TV — ~100. Попутно: Value Area по ОДНОЙ строке — единогласие 6/6 реализаций с
видимым алгоритмом (наш SINGLE подтверждён; парный CBOT не кодирует никто); по
переваливающей строке школа расколота (двое добавляют, как наш `build()`, двое
останавливаются, как наш `build_tv` и справка TV); ничью ПОК никто не отказывает —
py-market-profile берёт максимум ближе к середине диапазона, Pine — нижнюю строку; наш
`NotReady` строже всех, прецеденты тай-брейка записаны на случай сходимости с TV.*

**2. Побитовость против верности.** Единственный недокументированный шаг прибора —
раскладка объёма intrabar-бара по строкам. Реализована раскладка по сделкам: она вернее
прибора, но может расходиться с экраном владельца. Альтернатива — эмулировать лестницу
младших ТФ (у нас есть все бары). Выбор записан за владельцем; текущее решение — сделки.

**3. Переключение.** После ответа на 1: `levels.build_level` переводится с `build()` на
`build_tv(hist, bottom=границы структуры, top=…, rows=N)`, изменение предъявляется
диффом повтора (§10.6 условие 2) — по 175 структурам из E-070 ожидание: сдвиг ПОК у
~70-80% уровней. Это ожидание, не замер.

## Что уточнено против прежних документов

* `04-poc-corrected.md` и §2.2 FOUNDATION говорят «по умолчанию 24 строки» со ссылкой на
  внешнее допущение — допущение ОСЛАБЛО: официального умолчания нет, живой TV показывает
  ~100. Формулировка §2.2 поправлена.
* FRVP и VRVP — одна расчётная машина, различие только в источнике диапазона (ручное
  выделение против видимой области). Для стр. 63 курса это значит: "VRVP для поиска,
  фиксированный для ТВХ" — различие удобства, не расчёта.
* Up/Down Volume у TV — не покупки/продажи, а НАПРАВЛЕНИЕ intrabar-свечи (весь объём
  свечи в одну сторону); две страницы справки противоречат друг другу при close = open.
  У нас сторона не хранится (§3, запрет CVD) — и по смыслу TV она и не сторона сделки.
